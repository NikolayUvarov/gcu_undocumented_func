# Анализ раскладки ELF и плоских бинарников

Все данные получены на текущей сборке (`./02_build.sh`, 2026-09-17). Команды: `readelf -S/-l/-r/-s`, `llvm-objdump -d`, `xxd`.

## Находка 1 (критично): `_start` ядра лежит по смещению 0x60, а загрузчик прыгает на 0

`readelf -S kernel`:
```
[ 1] .dynsym   0x000000  size 0x18
[ 2] .gnu.hash 0x000018  size 0x1c
[ 3] .hash     0x000034  size 0x10
[ 4] .dynstr   0x000044  size 0x01
[ 5] .rela.dyn 0x000048  size 0x18
[ 6] .text     0x000060  size 0x235   <-- _start здесь
[ 7] .dynamic  0x000298
[ 8] .got      0x000378  size 0x08
Entry point 0x60
```

`xxd -l 0x60 kernel.bin` — первые 96 байт: нули, `01 00 00 00 ...`, `78 03 ...`, `50 02 ...` (содержимое хеш-таблиц и RELA-записи). Это то, что исполняется первым после `transmute(kernel_addr)` в `bootloader/src/main.rs:56`.

Почему у app иначе: у app есть `.rodata`, и LLD кладёт orphan-секции с флагом `A` рядом с ней (после `.text`); у ядра `.rodata` пуста, и orphan-секции ранга «только чтение» встали перед `.text` (ранг ниже, чем у `AX`). Entry app = 0x0 — корректно.

Почему это могло «работать»: нули декодируются как `add [rax], al`. Если в `rax` на момент прыжка лежит `kernel_addr` (выровнен на страницу → `al = 0`), инструкции ничего не меняют, и исполнение «сползает» до `_start`. Это зависимость от случайного содержимого регистра, а не корректный запуск. При любом изменении кода загрузчика или размера секций поведение изменится.

## Находка 2 (критично): вызов `memset` идёт через GOT, а слот GOT в плоском бинарнике нулевой

`llvm-objdump -d kernel`:
```
13b:  callq *0x237(%rip)   # 0x378  (.got)
```
`readelf -r`: одна релокация `R_X86_64_RELATIVE` по адресу `0x378` с addend `0x250` (= адрес `memset`).
`xxd -s 0x378 -l 8 kernel.bin` → `00 00 00 00 00 00 00 00`.

LLD по умолчанию не записывает addend в место релокации (`--no-apply-dynamic-relocs`), а никто в рантайме релокации не применяет. Итог: `core::ptr::write_bytes(fb_ptr, 0, ...)` в `kernel/src/main.rs:38` — это `call` по **физическому адресу 0**. У app то же самое: `callq *0x3c6(%rip) # 0x468`, слот нулевой.

Причина, по которой вызов вообще идёт через GOT: `memset` — скрытый локальный символ из `compiler_builtins`, но релокация в объектном файле — нерелаксируемая `R_X86_64_GOTPCREL`, потому что для таргета `x86_64-unknown-none` `relax-elf-relocations` выключен.

## Проверенное исправление (эксперимент в scratchpad, в проект не вносилось)

1. Флаг `-Z relax-elf-relocations=yes` → `addr32 callq 0x240 <memset>`, секция `.got` пустая, `.rela.dyn` отсутствует.
2. В `linker.ld` явно перечислить служебные секции **после** `.bss`:
   ```ld
   .dynsym : { *(.dynsym) }  .gnu.hash : { *(.gnu.hash) }  .hash : { *(.hash) }
   .dynstr : { *(.dynstr) }  .rela.dyn : { *(.rela.dyn) *(.rela.*) }
   .dynamic : { *(.dynamic) } .got : { *(.got .got.*) }
   /DISCARD/ : { *(.eh_frame) *(.comment) }
   ```
3. В `02_build.sh` дампить только полезные секции: `llvm-objcopy -O binary -j .text -j .rodata -j .data`.

Результат: kernel — `Entry 0x0`, `There are no relocations in this file`, `kernel.bin` = 565 байт, начинается с `55 41 57 41` (`push rbp; push r15`). app — `Entry 0x0`, `app.bin` = 808 байт, `SIN_TABLE` адресуется через `lea 0x138(%rip)`.

Альтернатива без `-Z`-флага: `-C relocation-model=static` + `--no-pie` убирает релокации, но GOT-вызов остаётся с абсолютным адресом `0x1f0` (проверено) — годится только при загрузке по фиксированному адресу (`AllocateType::Address`). Не рекомендуется.

Оформлено как issue 001. Запуск в QEMU после правки — обязательная проверка (здесь QEMU нет).

## Находка 3: `.bss` в плоском бинарнике

`llvm-objcopy -O binary` не пишет хвостовую NOBITS-секцию. Даже при объявленном в `linker.ld` `.bss`:
- страницы выделяются из `kernel_bytes.len()` — места под `.bss` может не быть;
- память из `allocate_pages` не гарантированно нулевая — статики получат мусор.

Для `static mut`/аллокатора нужно либо ELF-загрузчик (`p_memsz > p_filesz` → зануление), либо в плоском варианте: символы `__bss_start/__bss_end` в `linker.ld`, передача размера в загрузчик, выделение `memsz` страниц и `write_bytes(0)`. → issue 002/003.

## Что в раскладке нормально

- `.text._start` действительно первый в `.text` (проверено дизассемблером).
- Обращения к `.rodata` RIP-relative — PIC работает, бинарники грузятся по любому адресу.
- Стек: ядро и app работают на стеке UEFI-загрузчика (после `exit_boot_services` он остаётся валидным). Собственного стека нет — для многозадачности потребуется.
