## Observed device and missing evidence

The Ryzen reports PCI `02:00.0`, `10ec:8168`, revision `0c`, subsystem `10ec:0123`. In the supplied boot inventory, BAR2 is a 4096-byte MMIO region, BAR0 is I/O and BAR4 contains MSI-X. These are observations from build `e6730d7a`; discover the current addresses through the platform instead of assuming them. Legacy IRQ line `255` is unusable. MSI and the exact variant's requirements need the platform integration task.

PCI revision is insufficient to choose a MAC/PHY sequence. TxConfig at MMIO offset `0x40` supplies the raw revision bits; the XID is `(TxConfig >> 20) & 0xfcf`. The library preserves both values. A report should label unavailable/all-ones data as a failed observation, not a supported or unsupported chip. The extraction follows the primary [Linux v6.12 identification path](https://raw.githubusercontent.com/torvalds/linux/v6.12/drivers/net/ethernet/realtek/r8169_main.c), `rtl_init_one`.

For a MIND report, first verify exact PCI ID, a memory BAR with at least `0x44` bytes and an accessible, powered MMIO mapping. Read only the aligned 32-bit TxConfig register with volatile access; do not alter BAR assignment, reset, power state, PHYAR or OCP to obtain this observation. `rtl8168::identity` merely decodes a value or previously collected snapshot; it has no MMIO accessor. These conditions are the reporter's responsibility. The offset is independently listed as `RL_TXCFG` in [FreeBSD releng/14.2's register header](https://raw.githubusercontent.com/freebsd/freebsd-src/releng/14.2/sys/dev/rl/if_rlreg.h).

[213-KRN-0113](../issues/213-KRN-0113-realtek-boot-identification.md) implements this x86 report path with actual UC identity-map checks and ungranted/non-mastering guards and D0 when PM exists. It may temporarily enable only PCI Command memory decode, then restores it and preserves Status flags; no MMIO, reset, power or PHY write occurs. Eight host guard tests, a page-table-walk test and the kernel build pass. This MIND report path still needs validation on the Ryzen; the actual identity below was collected through Linux.

Under Linux, `scripts/hardware/rtl8168_probe.py` uses the bound `r8169` driver's read-only ethtool dump, verifies its driver/BDF and 256-byte layout, and saves raw evidence privately. See task 0030 for the command.

## Descriptor format

The 16-byte little-endian descriptor has two 32-bit control/status words followed by a 64-bit DMA buffer address. Word 0 uses OWN bit 31, final-ring marker bit 30, first-frame bit 29 and last-frame bit 28. The implementation uses 256 descriptors per ring and 256-byte ring alignment. These facts are cross-checked against [FreeBSD's descriptor and ring definitions](https://raw.githubusercontent.com/freebsd/freebsd-src/releng/14.2/sys/dev/rl/if_rlreg.h), `rl_desc`, `RL_8169_*_DESC_CNT` and `RL_RING_ALIGN`.

RTL8168 RX length is the low 14 bits and includes the 4-byte FCS. RX error bits are 22 (watchdog), 21 (summary), 20 (runt) and 19 (CRC). Do not directly use the shared 8139 RX status constants: FreeBSD's `re_rxeof` shifts RTL8169-family status before testing those constants. Sources: [FreeBSD receive path](https://raw.githubusercontent.com/freebsd/freebsd-src/releng/14.2/sys/dev/re/if_re.c), [Linux receive path and status definitions](https://raw.githubusercontent.com/torvalds/linux/v6.12/drivers/net/ethernet/realtek/r8169_main.c), `rtl_rx` and `rtl_register_content`.

The descriptor implementation copies no upstream driver implementation, firmware or PHY tables. Its source references establish hardware facts; MIND's bounded queue implementation is independent. The separate controller adaptation below retains its upstream licence notices. Provenance is recorded in [THIRD_PARTY.md](../THIRD_PARTY.md).

## Implemented memory and ownership contract

`rtl8168::rings::Rings` takes one caller-owned coherent DMA mapping on x86-64. It validates a non-null, 256-byte-aligned virtual base and physical address, enough mapped bytes, address overflow and the complete physical range below 4 GiB. Its fixed layout is:

| Region | Offset | Bytes |
|---|---:|---:|
| TX descriptors | 0 | 4096 |
| RX descriptors | 4096 | 4096 |
| TX buffers | 8192 | 524288 |
| RX buffers | 532480 | 524288 |
| Total | 0 | 1056768 |

Each buffer is 2048 bytes. Initialization zeroes the mapping and arms RX descriptors while the device is stopped. It performs no device access. The unsafe constructor requires the caller to keep the mapping coherent, alive and exclusively associated with this object and one ownership-obeying NIC. CPU aliases and overlapping send/output slices are forbidden. The caller must stop DMA before reusing the region, even if the Rust object has already been dropped. Dropping the object does not quiesce the NIC or free memory. This API intentionally does not claim that a Rust lifetime can enforce an external device's lifetime.

`send` handles one 14–1514-byte Ethernet frame, pads to 60 bytes, and publishes one descriptor. It returns full/owned errors without overwriting pending data. The service must kick the NIC after successful publication. `reclaim` returns at most one completed descriptor in submission order, preserving raw completion status for later driver accounting. A completion establishes buffer reuse, not receipt by the remote host.

`receive` examines exactly one descriptor per call. It drops error/fragmented/invalid-length frames, copies 60–1514 payload bytes while the CPU owns the buffer, removes the FCS, then rearms. A short output buffer leaves the descriptor CPU-owned for retry; the service must retry with a `MAX_FRAME` buffer instead of repeatedly using the same insufficient client buffer. It does not search indefinitely for a good packet. A service must still limit repeated calls per turn, including dropped packets, as done by the network-stack work budget.

Descriptor access is volatile. Full compiler/hardware fences order payload/address/control access before OWN publication, after observing completion, and before the caller can issue a doorbell. RX OWN is never returned before copying or explicitly discarding the frame. These choices target coherent x86-64 memory; the crate rejects compilation for other architectures. Non-coherent DMA, cache maintenance, offloads, VLAN insertion/stripping, tagged frames above the maximum and jumbo frames are outside this implementation's contract.

## Bounded RTL8168G service

`rtl8168/src/controller.rs` adapts the reviewed RTL8168G branch of FreeBSD's `re` driver and standard MII negotiation. It selects only XID `0x4c0` and the observed PHY ID `0x001cc800`. This product includes software developed by Bill Paul. The BSD-4-Clause copyright notices, conditions, disclaimer and advertising acknowledgement are retained in [LICENSES/BSD-4-Clause-realtek.txt](../LICENSES/BSD-4-Clause-realtek.txt); [THIRD_PARTY.md](../THIRD_PARTY.md) records the adaptation.

Startup first requires an exact device BAR grant with PCI memory decoding enabled and I/O/bus mastering disabled. Init supplies the PCI device index as its decimal argument. The controller reads identity and MAC before any MMIO write, disables RX acceptance and interrupts, gates RXDV and resets the MAC. Reset polling has a 100 ms deadline; each PHYAR operation has a 50 ms deadline and a finite iteration bound, with at least a 1 ms scheduler sleep between transactions. PHY reset polling is finite too. All these operations share one 1500 ms startup budget. Scheduler delay can exceed a requested sleep, but no new transaction begins after the budget expires. Unknown/inaccessible identity, invalid MAC, an unexpected PHY or timeout leaves the service unavailable with an explicit reason.

The observed PHY `0x001cc800` is more specific than a revision number. FreeBSD's pinned [OUI decoder](https://raw.githubusercontent.com/freebsd/freebsd-src/16a79708d089423ec0c3d32f25e7ca97ae58e97b/sys/dev/mii/mii.c) and [model list](https://raw.githubusercontent.com/freebsd/freebsd-src/16a79708d089423ec0c3d32f25e7ca97ae58e97b/sys/dev/mii/miidevs) select OUI `00e04c`, model `0`, revision `0`: RTL8251. `rgephy_reset` does not apply the later RTL8211 PCR/EEE branches to this revision, and `rgephy_load_dspcode` explicitly excludes RTL8251. Therefore no selected legacy DSP table is being silently omitted from this FreeBSD PHY baseline. This does not establish equivalence to Linux's selected vendor initialization.

The PHY baseline wakes registers 31/14, performs standard BMCR reset, advertises the observed BMSR 10/100 capabilities and 1000BASE-T half/full duplex, and starts negotiation. It does not wait for cable/link. No firmware is embedded, fetched or loaded by this baseline. Unlike Linux's identified path, this sequence uses FreeBSD PHYAR access and omits Linux PHY-OCP/ERI/EPHY tuning, EEE handling and the external PHY patch. It also omits FreeBSD's PCI maximum-read-request tuning. These are explicit hardware-validation risks; successful compilation or a register model cannot establish that a cold Ryzen boot needs none of them. If the baseline cannot establish a stable link, inspect its recorded failure and use reviewed compatible source material for the next change instead of guessing PHY writes.

After successful reset, the driver initializes the coherent rings, programs their addresses and configures MTU 1500, no checksum/segmentation/VLAN offloads, individual/broadcast/multicast receive and bounded interrupt moderation. `program()` leaves engines disabled in `Armed` state. Only a successful `platform::resume(index)` authorizes `enable()` to write RX/TX enable. Kernel task 213-KRN-0114 provides the MEM-only initial BAR grant, verifies this owned-device transition and controls boot/restart DMA lifetime. The service keeps all DMA mappings after any resume attempt, including failure. On runtime faults it requests engine stop, asks the kernel to quiesce PCI, logs the result and retains memory. A stop request or elapsed timeout alone never permits reclamation.

`rtl8168/src/main.rs` implements `net.wit` 1.3 info/link, send/receive, up to four deferred waiters, counters and the existing read-only badge rules. Unsupported shared-ring attach drops the transferred capability and returns `Invalid`; offloads are zero. Each service turn reclaims at most 64 TX descriptors and consumes at most 64 RX descriptors, followed by IPC handling; a 16-frame software queue bounds pending receive storage. MSI is used when granted/bound; otherwise the service polls every 20 ms. Absent/down/full conditions return `NoDevice`, `Busy` or `Empty`. Five seconds without any completion while TX is pending stops the service with counters; recovery requires the normal supervised restart, with verified kernel quiescence before old DMA reuse. This baseline does not autonomously reset a hung NIC.

The release executable builds for `x86_64-unknown-none`. After own-branch commit `e89fb569` was published through fast-test merge `91059a37`, all sixteen host tests passed (eight existing queue/identity cases and eight new controller cases). The new cases cover: identity refusal without writes; finite reset with a frozen clock; MDIO/PHY failures; one total budget across successful slow transactions; exact PHY refusal; ring programming before a separate engine-enable step; device disappearance; and fault handling that preserves NIC-owned descriptors. These tests cover CPU-side behavior only. The new service still needs boot integration, network-regression runs and the actual Ryzen acceptance tests. No physical link, IRQ, packet-transfer or restart success is claimed.

### First hardware validation record

The maintainer writes the published hardware-test branch under the normal workflow; agents do not build or test `fast-test`. Record the exact build, cold versus warm boot, connected cable/switch, and whether Ubuntu or firmware previously initialized this NIC. Keep raw hardware inventories and MAC-bearing output private.

1. Capture `dmesg`, `ps`, `devices`, `faults` and `irqs`. Require the Realtek identity and driver XID/PHY to match, a successful driver start, and no reset/MDIO/PCI/mastering/quiesce error. `MODE=MSI` only reports binding; interrupt counters must establish actual delivery. Poll fallback is a separate configuration.
2. Read `net` and `ip`: distinguish link down, no DHCP lease, no gateway, and a broker-policy refusal. Check the card slot selected by the KRN integration. Do not change firmware/PHY configuration merely because an address is missing.
3. With a lease, use `ping <gateway>` and a known reachable LAN peer, then ping the MIND address from that peer. Record counts, losses and latency in both directions. Check an already-authorized `https <host> [path]` target through normal policy/TLS; a policy or certificate rejection is not a NIC success or failure by itself.
4. Run the task's sustained TCP plus ping and previously slow test workload for at least 30 minutes. Capture counters before/after, error logs and service responsiveness. The bounded software queue can drop bursts; report those drops explicitly rather than treating the run as lossless.
5. Exercise cable removal/reconnection and supervised driver restart separately. The current 5 s TX stall path retains memory and leaves the service unavailable until supervision restarts it; it does not claim automatic hardware recovery. Verify the KRN quiesce result before restart/reuse and whether the stack reacquires a lease and accepts new flows.

A failed reset or PHYAR operation is an initialization blocker; preserve the startup log before choosing the next reviewed sequence. A running controller with link down directs the next investigation toward PHY/power/negotiation and cable evidence. A link with no received frames directs it toward DMA/RX/interrupt evidence. These are investigation branches, not assertions that the hardware already passes.
