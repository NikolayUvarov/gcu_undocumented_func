# Рецензия MIND CORE и Marain — 21 сентября 2026

**Вывод:** Конституция v1.4 и RFC Marain v0.2 — содержательная основа для проектирования и прототипа. Конституция v1.5 и RFC v0.3 в текущем виде хуже подходят на роль заменяющих спецификаций: сокращение убрало существенные условия, а новая гарантия `reconcile` некорректна. Рекомендую строить следующую полную редакцию на v1.4/v0.2, перенеся в неё только уточнённые дополнения.

Это рецензия требований и проектных решений. Реализация, её производительность и доказательства здесь не проверялись. Внешние источники изучены 21.09.2026; рекомендации для MIND CORE ниже являются инженерными выводами, а не автоматически наследуемыми гарантиями чужих проектов.

## 2. Блокирующая ошибка: reconcile не может возвращать власть по тайм-ауту

**Место:** [RFC v0.3, §7.5, строка 20](RFC_001_Marain_v0.3.md). Сопоставить с [v0.2, §7.3 и §7.5, строки 180–206](RFC_001_Marain_v0.2.md).

Новая версия обещает: если тайм-аут или разрыв подтверждён, исключительное владение из escrow будет возвращено отправителю. Подтверждается здесь отсутствие связи, а не отсутствие приёма, выполнения или продолжающегося доступа на другой стороне.

Контрпример:

1. Шлюз передал получателю право использовать ресурс.
2. Получатель начал действие; ответ потерялся.
3. Отправитель зафиксировал тайм-аут и получил право обратно.
4. Получатель продолжает действие либо его отложенная команда доходит позже. Исключительное управление нарушено.

Если escrow ещё не выпустил право получателю и может достоверно установить это по своему состоянию, возврат возможен. Если ресурс гарантированно отвергает старую эпоху, возможна новая выдача после fencing по определённому протоколу. Само слово «доверенный gateway» этих условий не создаёт. Контроль над будущими командами также не отменяет уже совершённый эффект и не возвращает потерянные данные.

В Chubby запоздалые запросы ограничиваются sequencer, проверяемым **принимающим сервером**; задержка перед повторной выдачей описана как несовершенная замена. Это непосредственно поддерживает необходимость fencing у исполнителя. [Burrows, Chubby, §2.4](https://www.usenix.org/legacy/event/osdi06/tech/full_papers/burrows/burrows_html/).

**Предлагаемая замена нормы:**

> `reconcile` выполняет авторизованную сверку результата операции и состояния владения по operation ID. Тайм-аут и разрыв связи сами по себе не разрешают возврат исключительного владения. Возврат допускается при подтверждённом непринятии передачи либо после протокола, исключающего прежний доступ и определяющего судьбу принятых команд. При недостаточности свидетельств сохраняется `OutcomeUnknown`; ресурс остаётся учтённым. Условия завершения сверки, её бюджет и реакция на длительную недоступность задаются профилем.

Нужно различать два результата: **итог действия** и **действующего владельца ресурса**. Можно уже безопасно сменить владельца, но ещё не знать результат прежней команды. `reconcile`, возврат ресурса, retry и компенсация — разные операции с разными полномочиями. Квота нерешённых записей должна ограничивать admission новых операций; по её исчерпанию нельзя просто забывать старые обязательства.

Кроме того, фраза v0.3 §7.3 «транспорт имеет ровно два исхода» потеряла ограничение на **локальный `try_send`**. Для удалённой операции наблюдаемый результат может остаться неизвестным. Вернуть точную область действия из v0.2.

## 4. Что потеряно в Marain v0.3

Ссылки на старый пример (§12) и альтернативы (§14) есть. Общего правила «весь остальной текст v0.2 действует без изменений» нет. Поэтому краткие разделы нельзя уверенно читать как полную преемственную спецификацию.

| Разделы v0.2 | Что необходимо восстановить |
|---|---|
| §§1–2 | Границы обещаний, модель угроз, распределение гарантий между compiler/runtime/kernel/service, проектный статус примеров |
| §3 | Порядок слева направо, overflow, trap против Result, UTF-8, эффекты замыканий, мономорфизация экспортов, пределы чистоты |
| §§4–5 | Правила строки эффектов handler; нулевой resume и очистка; запрет escaping continuation/borrow; явные spawn bindings; отсутствие Cap внутри копируемого val; drop не равен revoke |
| §6 | Каскады ARC, ограниченная очередь очистки, учёт host calls, принудительное прерывание; `rt` за пределами MVP |
| §7 | Автомат Uncertain, receipt против эффекта, возврат payload при Rejected, атомарность enqueue/MOVE, исключение удалённого MOVE из начального профиля, пределы session types |
| §8 | Версия семантики и канонического кодека; состав CodeID/BuildKey; рекурсивные группы; test vectors; retention; проверка AOT при запуске |
| §§9–10 | Inbox/outbox и нерешённые эффекты в checkpoint; rebind с текущей авторизацией; запрет повторных реальных эффектов при replay; полный состав недетерминизма |
| §11 | Версионный ABI-профиль; отсутствие implicit WASI; лимиты уже при lifting; companion-контракт поведения; граница FFI |
| §§15–17 | Конкретные критерии приёмки, отрицательные сценарии, открытые вопросы и карта соответствия Конституции |

Последствие — разные реализации могут честно следовать v0.3 и расходиться по переполнению, отмене, повтору действия, очистке ресурсов и идентичности кода.

## 5. Новые дополнения: что принять, что уточнить

### SHARE_RW: ограничение правильное, новизна преувеличена

Запрет в безопасном Core MVP **уже есть** в [v0.2 §5, строка 125](RFC_001_Marain_v0.2.md). Его стоит сохранить. Размещение опасного доступа в адаптере с узкими правами полезно, но доверенность адаптера не устраняет изменение буфера злоумышленником.

**Требовать от адаптера:** ограниченную частную копию с проверкой именно этой копии; либо принудительную неизменяемость на время использования; либо отдельно обоснованный конкурентный алгоритм. Мьютекс помогает только против участников, соблюдающих протокол. Копия конкурентно изменяемой структуры сама по себе может быть несогласованной: её всё равно надо валидировать, включая связи между полями. [SafeFetch, USENIX Security 2024](https://www.usenix.org/conference/usenixsecurity24/presentation/duta).

В Конституции оставить инвариант 2.11. Конкретный запрет Core и допуск адаптеров описывать в профиле с перечислением, кто и какие режимы может использовать.

### Checkpoint receipts: полезная обязанность, недостаточная спецификация

Дополнение [v1.5 6.10, строка 18](MIND_CORE_Constitution_v1.5.md) делает поддержку checkpoint инфраструктурой более явной. Но «сверка очередей в момент снимка» не определяет согласованную точку между состоянием актора, очередью, опубликованным Head и внешним исполнителем.

Предлагаемая норма: профиль персистентного исполнения задаёт согласованный протокол checkpoint для состояния, очередей и нерешённых эффектов; ответственные компоненты предоставляют необходимые ограниченные операции. Механизм — quiescence, журнал, barriers или иной — описывается отдельно. Включать предметную логику checkpoint в ядро из этой нормы не следует.

Практический пример: Flink отдельно различает согласованность собственного состояния и результат во внешней системе; для end-to-end exactly-once требуется участие внешнего получателя. Переносить этот протокол на физический привод автоматически нельзя. [Apache Flink, exactly-once](https://flink.apache.org/2018/02/28/an-overview-of-end-to-end-exactly-once-processing-in-apache-flink-with-apache-kafka-too/).

### Проверка handles: сохранить, расширить точный контракт

Проверка типа, владельца и поколения **уже была** в [v0.2 §5, строка 119](RFC_001_Marain_v0.2.md), а текущей авторизации — в §4.3. Новая формулировка §11 v0.3 полезна как явное требование ко всем соответствующим ABI-переходам.

Однако три поля не заменяют проверку разрешённой операции, scope, состояния отзыва, протокола и квоты. Проверка и применение должны сохранять согласованность при конкурентном отзыве. Для stale handle нужен явный протокол повторного использования слота; слово «эпоха» без способа связывания с запросом не решает ABA.

Числовые индексы не должны быть секретом. Они выбирают права в защищённом контексте вызывающего домена. Угадывание индекса уже выданного этому домену права не является повышением полномочий; доступ к чужому контексту должен быть невозможен. Для взаимно недоверенных акторов внутри одного runtime надо назвать реальный механизм разделения, а не полагаться на сокрытие числа. [seL4: CSpace и invocation](https://docs.sel4.systems/Tutorials/capabilities.html), [WebAssembly: границы security model](https://webassembly.org/docs/security/).

## 6. Нормативность и редакционная дисциплина

**Конфликт статуса приложений.** [v1.4, строки 25–29](MIND_CORE_Constitution_v1.4.md) делает нормативными статьи, а приложения — пояснениями/предложениями. [v1.5, строка 4](MIND_CORE_Constitution_v1.5.md) объявляет нормативным инженерный профиль и перечисляет Б, В, Г, Д. При этом импортированный Б допускает альтернативы, Г содержит план, а Д — исторические SHA-256. Это существенное изменение правил соответствия, не оформление.

**Смешана нумерация.** v1.5 приложение Г ссылается на «фазы M0–M7» v1.4. У Конституции v1.4 этапы **0, I–VII**; M0–M7 принадлежат языковому RFC. Зависимости легко понять неверно.

**«Архив» не определён.** v1.5 говорит о переносе приложений А/Е/Ж в архив, но путь не дан. В просмотренном наборе они доступны внутри v1.4; отдельного указанного архива нет. Нужны обычные рабочие ссылки и фиксированная версия источника. Политика приоритета документов и словарь из v1.4 также исчезли.

**Что сделать:**

1. Публиковать полную нормативную редакцию и отдельное краткое резюме. Если выпускается только поправка, явно указать базовую редакцию, точные заменяемые пункты и правило наследования.
2. Сохранить иерархию: инварианты Конституции → архитектурные контракты → именованные платформенные/языковые профили → roadmap и обоснования.
3. Выдать требованиям стабильные ID; для каждого связать механизм, ответственный слой, предположения и свидетельство. Таблицы приёмки уже есть — их нужно трассировать, а не дублировать.
4. Вернуть определения ДОЛЖЕН/ЗАПРЕЩЕНО/ДОПУСКАЕТСЯ и приоритет при конфликте. RFC 8174 полезен как образец явного нормативного языка; соответствие IETF для русского текста заявлять не требуется. [RFC 8174](https://www.rfc-editor.org/info/rfc8174/).
5. Снять «финальная спецификация» с v0.3: грамматика, кодек и runtime-профиль из открытых вопросов v0.2 ещё не определены в новом тексте.

| Ранняя проверка протоколов | Моделировать revoke/MOVE/checkpoint/fencing до оптимизации; затем связать модель с fault tests реализации | Принимать успешный стенд за доказательство корректности всех исполнений | [AWS: How Amazon Web Services Uses Formal Methods](https://assets.amazon.science/67/f9/92733d574c11ba1a11bd08bfb8ae/how-amazon-web-services-uses-formal-methods.pdf) |

Это поддерживает направление v1.4, а не необходимость переписать всё заново. Для первого среза разумны одна платформа, COPY IPC, один Head-сервис и один восстанавливаемый актор. Zero-copy, межузловое исключительное владение и квалифицированный `rt` требуют самостоятельных профилей.

## 8. Лучшие практики для языка

**Сохранить небольшой Core.** ADT, Result, явные эффекты, affine-ресурсы, одноразовые продолжения, локальные автоматы и ограниченные акторы — связный набор. Но каждый механизм должен иметь правила совместного применения. Работа по линейности и effect handlers показывает реальные ошибки при их наивном объединении; запрет multi-shot в v0.2 — разумное упрощение. [Авторы Soundly Handling Linearity, POPL 2024](https://blog.sigplan.org/2024/08/12/soundly-handling-linearity/).

**Эффекты не заменяют авторизацию.** Сохранить разделение effect / handler / capability. `Net` показывает вид действия; получатель, срок, объём и право на делегацию остаются свойствами конкретного полномочия. Полный binding-план не обещает успешное выполнение после отзыва.

**ARC — стратегия памяти.** Perceus даёт конкретные результаты о reference counting, reuse и garbage-freedom в своей модели. Для MIND CORE это основание исследовать стратегию, а не доказательство hard real-time. Восстановить из v0.2 пределы каскада освобождения и квоты отложенной очистки. [Perceus, первичная публикация](https://www.microsoft.com/en-us/research/publication/perceus-garbage-free-reference-counting-with-reuse/).

**WIT — интерфейсный слой.** WIT определяет интерфейсы и типы, включая resource ownership/borrow; поведение протокола он не специфицирует. MIND companion-контракт должен отдельно задавать ошибки, порядок, лимиты, отмену и права. [WIT Reference](https://component-model.bytecodealliance.org/design/wit.html).

**Wasm metering не охватывает всё исполнение.** Документация Wasmtime прямо отмечает: fuel и epochs не прерывают блокировку внутри host call. Значит, нужны ограничения и отмена на host-стороне плюс учёт её CPU/памяти. Это ещё один довод вернуть развёрнутый §6.2 v0.2. [Wasmtime: blocking host calls](https://docs.wasmtime.dev/api/wasmtime/struct.Config.html#method.epoch_interruption).

**Хэши определений полезны при точной семантике.** Unison подтверждает работоспособность идеи определения по хэшу с именами как отдельными метаданными. Для Marain сохранить различия SourceCID/CodeID/BuildKey/ArtifactCID и независимые test vectors. Равенство идентичности не заменяет проверку совместимости протокола, bindings и схемы состояния. [Unison: The big idea](https://www.unison-lang.org/docs/the-big-idea/).

**Новый язык должен пройти сравнение с альтернативой.** Рекомендация: выполнить одинаковый сценарий на исследовательском Marain и существующем языке с generated MIND bindings. Сравнивать диагностируемые ошибки, объём доверенного кода, память, стоимость IPC, отладку и сопровождение. Начать сравнение на M0; пилот M6 использовать для итогового решения. Rust с bindings — разумная базовая точка для этого проекта, но не автоматическая замена всем эффектным/протокольным возможностям Marain.

## 9. Что ещё доработать даже в v1.4/v0.2

Эти вопросы не появились из-за сокращения; исходные документы сами относят часть из них к будущим этапам.

1. **Формальная семантика Core.** Зафиксировать грамматику, kind/ownership-правила, захваты замыканий, полиморфные эффекты, handler nesting, нулевой resume и trap cleanup. Пример отрицательного требования: копируемое значение не может скрыть Cap внутри замыкания или параметрического контейнера. Нужны reference evaluator и сравнение с Wasm backend, уже предусмотренные M0–M3.
2. **Точный профиль исполнения.** Выбрать версии runtime/Component Model/WIT, разрешённые imports, лимиты lifting, metering и отмену host calls. Указание «Wasm» недостаточно. Проверка локальной модели на host-стенде не удостоверяет аппаратный MOVE/DMA.
3. **Один полностью расписанный протокол checkpoint.** Где commit? Кто сохраняет receipt? Когда разрешён ACK? Что после crash между эффектом и записью результата? Как переживают restore revoke и fencing? Зафиксировать модель хранения и точку, после которой забываются dedup-записи; старые повторы после удаления должны отвергаться либо иметь явно ограниченную гарантию.
4. **Согласовать пример logging с §7.5.** WIT §11 v0.2 возвращает `result<_, log-error>`, включая `unavailable`, но не показывает неизвестный результат append. Либо companion-контракт доказывает отказ до commit, либо API/протокол должен представлять operation ID и неопределённый исход. Это недоопределённость примера, а не доказанная ошибка реализации.
5. **Уточнить роль языка в cognitive plane.** Core без floats подходит для оркестрации, но не описывает собственные tensor/GPU-вычисления. Для пилота проще считать их отдельным ограниченным сервисом: версионированные модель/входы, бюджет, отмена, происхождение результата и объявленные пределы replay. Это предлагаемая декомпозиция, не обязательство немедленно расширять язык.
6. **Очистить полемические обоснования v1.4.** В приложении Е.1 тезисы «поверхность атаки равна объёму привилегированного кода» и «цена IPC снята практикой» чрезмерны; в Е.3 ACL, UID/GID и root сведены в один тезис о «структурной нерешаемости confused deputy». Лучше описать конкретные ambient-authority и deputy-сценарии. Нормы 1.6 и 3.8–3.10 уже точнее этих обоснований. Не превращать инженерный выбор в универсальную оценку всех ОС.

Это предлагаемые проверки, не результаты выполненных тестов.
