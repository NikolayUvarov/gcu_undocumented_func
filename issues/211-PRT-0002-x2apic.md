# 211-PRT-0002 — The local APIC in x2APIC mode

**Type:** porting (kernel, x86-64) · **Owner:** `PRT` · **Priority:** P1 · **Status:** open · **Blocked by:** — · **Main task:** [211](211-intel-pc-from-a-sata-ssd.md) · **Constitution:** MC-12.1

## Problem

The kernel drives the local APIC through its xAPIC registers in memory. If the firmware hands over the APIC in x2APIC mode (`IA32_APIC_BASE` bit 10), the kernel stops with `x2APIC is not supported yet` (`kernel/src/arch/x86_64/cpu.rs:78`). The message goes only to COM1. Many current Intel boards leave x2APIC on, so this may be the first thing the maintainer's PC hits.

## Plan

- Detect the mode at boot. In x2APIC mode, use the MSR interface:
  - ID, EOI, the timer, and the ICR as one 64-bit write with a 32-bit destination;
  - IPIs addressed by x2APIC ID, read from the MADT's x2APIC entries (type 9) as well as the xAPIC ones (type 0).
- Keep xAPIC mode where the firmware leaves it, as QEMU does by default.
- The 255-CPU limit of issue 171 rises where x2APIC is on. That stays a statement only if a run with more than 255 IDs exists; otherwise the profile keeps 255.
- Tests:
  - the suites in QEMU with `-cpu …,+x2apic` and the firmware switching to x2APIC (OVMF does when asked);
  - one group in `scripts/ci_local.sh` and CI.

## Acceptance criteria

The kernel boots and runs the `normal`, `smp` and `busy` suites with the APIC in x2APIC mode in QEMU, and in xAPIC mode as before. The profile states which mode was tested where.
