# 550-DRV-0005 — A USB Ethernet class driver: CDC-ECM and CDC-NCM

**Type:** driver · **Owner:** `DRV` (open) · **Priority:** P2 · **Status:** open · **Blocked by:** — for the driver; for the check with `netstack`, the `NET` request "several network interfaces" ([requests-NET.md](requests-NET.md)) and `init`'s part (`KRN`) · **Main task:** [550](550-network-on-real-hardware.md) · **Constitution:** MC-12.1, MC-2.3, MC-3.3, Appendix B.6

Numbered by the kernel session at the maintainer's request (2026-10-08); the track is open.

## Problem

A USB Ethernet adapter is the quickest way to put the MacBook Pro, and most machines with USB, on a wired network. Many adapters offer a standard USB class for it:

- CDC-ECM (Ethernet Control Model): a communications interface of class 2, subclass 6;
- CDC-NCM (Network Control Model): class 2, subclass 13;
- in both, a data interface of class `0x0A` with the bulk endpoints.

No driver for them exists, and `usb_host` cannot reach them yet:

- It reads and sets only the first configuration (`SET_CONFIGURATION` with the first descriptor's value, `usb_host/src/main.rs`). Some adapters, many with a Realtek RTL8153 among them, list a vendor configuration first and the CDC one after it.
- It records only alternate setting 0 of each interface. A CDC data interface has no endpoints in setting 0; its bulk endpoints are in setting 1.
- It serves classes 3 and 8 only (`SERVED`), and a badge names one class (`mind::usb::class_of`).

## Plan

**In `usb_host`** (part of this task, in the same open track):

- Read every configuration (`bNumConfigurations`) and set the first one with an interface a class driver serves. A device with none keeps its first configuration.
- Record the alternate settings of an interface and select one when the class driver asks: `SET_INTERFACE` and the controller's endpoint set-up together (xHCI, and EHCI once 211-DRV-0004 lands). This is a new call in `idl/usb.wit`, version 1.1, with the generated files regenerated by `scripts/mind_idl.py` (MC-2.3).
- A badge for network class drivers (`BADGE_NET`, proposed). It claims a communications interface of subclass 6 or 13 together with the data interface its union descriptor names. RNDIS's control interface is class 2 too (subclass 2, protocol `0xFF`); it is not claimed.

**The driver** (`usb_net`, proposed name), a class driver like `usb_storage`:

- reads the functional descriptors: header, union, and Ethernet networking, whose `iMACAddress` string (12 hex digits) gives the MAC address;
- ECM: sets the packet filter (`SET_ETHERNET_PACKET_FILTER`), selects setting 1 of the data interface, and moves one Ethernet frame per bulk transfer, IN and OUT;
- NCM: reads `GET_NTB_PARAMETERS`, and packs and unpacks frames in 16-bit transfer blocks (NTH16 and NDP16);
- polls the interrupt IN endpoint (`reports`) for notifications: `NETWORK_CONNECTION` (link up or down) and `CONNECTION_SPEED_CHANGE`;
- serves `idl/net.wit` 1.2 to `netstack` as `virtio_net` does: `info` with the MAC address, MTU and link, `send`, `receive`, `wait`, and the frame ring (`attach`, `kick`). It offers no offloads (`offloads` is 0). So `netstack` needs no new interface for it; taking it as a card is the `NET` request;
- answers `no-device` before an adapter is plugged in and after it is pulled out, and claims a new one when it appears.

One adapter per driver instance; a second instance for a second adapter comes later.

**`init`** (a `KRN` task, numbered when needed): starts the driver at boot with a `usb_host` client under the new badge and a region for the frame ring, and hands its endpoint to `netstack`.

**Tests:**

- QEMU's `usb-net` device, which offers CDC-ECM and RNDIS, on `qemu-xhci` with user networking: a `qemu_smoke` suite (`usbnet`, proposed) on x86 and aarch64. The driver claims the ECM interfaces, `netstack` gets a DHCP lease, and `ping` and `fetch` to 10.0.2.2 work. The device is removed through QMP and added again; the link goes down and comes back. Which configuration QEMU lists first is checked when the suite is written; the choice of configuration gets a host test either way.
- NCM: QEMU has no NCM device. The transfer-block code gets a host test (`tests/*_host.rs`), and the device is checked on hardware.
- The MacBook Pro with a CDC-ECM or CDC-NCM adapter.

## Acceptance criteria

- The `usbnet` suite passes on x86 and aarch64, and the `usb` suite still passes.
- On the MacBook Pro, the adapter's MAC address and link show in `net` and `ip`, `netstack` gets a lease, and `https` fetches a page. The adapter's IDs and protocol are recorded with the run.
- `docs/profile` names the driver, its tests and the configurations they ran on.
