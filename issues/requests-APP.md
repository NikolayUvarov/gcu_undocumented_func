## The shell asks for `keystore`'s passphrase at boot, and sets or changes it (for 308-NET-0055), once `init` lends the badge

Numbered on 2026-11-10 as [308-APP-0130](../issues-done/308-APP-0130-the-shell-asks-for-keystores-passphrase.done).

**Asked by** NET (made by STO) on 2026-11-10, for [308-NET-0055](../issues-done/308-NET-0055-keystores-passphrase-without-a-tpm.done). **Waits for** [308-KRN-0205](../issues-done/308-KRN-0205-the-boot-waits-for-keystores-passphrase.done), which grants the shell a `keystore` client badged `BADGE_KEY_PASSPHRASE` (6, `mind::network`) and starts the shell before the services that need the device key.

- **What `keystore` gives** with `idl/keystore.wit` 1.6, in `main` since round 80:
  - `key-state`, any client's: `held`, `waiting` or `none`, answered at once;
  - `unlock(passphrase)` and `passphrase-set(old, new)`, for badge 6 alone; a passphrase is 8 to 128 bytes;
  - `denied` for a wrong one; from the third wrong one in a row, `budget` until a wait that doubles from 1 s up to 60 s has passed.
- **Asked of the shell:**
  - **at boot,** while `key-state` says `waiting`:
    - say why the boot waits, in one line;
    - read the passphrase without echo, as 000-APP-0126 reads a secret, and call `unlock`;
    - on `denied` or `budget`, say so and the wait, and ask again;
  - **a command to set or change it,** asking for the old one (none the first time) and the new one twice, each without echo, then `passphrase-set`;
  - **no passphrase on a command line, in the history or in a log,** and the shell's copies wiped once sent. The generated client wipes its call buffer (000-KRN-0226).
- **Why:** without it no task can type the passphrase, so a machine without a TPM keeps its device key unsealed on the boot disk.
- **Checked by** a suite that types it over the serial console, as it types every command. The `tls` suite's `locked_file_check` already places a sealed file from the host.

## The shell starts a program in a memory domain (for 312)

Numbered on 2026-11-12 as [312-APP-0134](312-APP-0134-a-program-started-in-a-memory-domain.md).

**Asked by** STO on 2026-11-12, for [312](../issues-done/312-the-minds-memory.done)'s QEMU criterion "a stand-in agent writes and reads its memory; forgetting frees what it should; another domain refused without a grant".

- **What there is:**
  - a memory domain is a set of names, pins and blocks under a key of its own (308-STO-0023);
  - its owner gets a client of it from the store, `blockstore.wit`'s `domain-client(id, cap)`, minted with the owner's rights. Through it a program reaches that domain alone: a domain's client may make, open, list, measure or forget no domain (`rights`, the `store` suite's domains check);
  - `blocks -d <id>` takes such a client for itself, but it holds the shell's client of the volume all the same;
  - the shell lends a program its own client of the volume in `SLOT_BLOCKSTORE` (`REQUEST_BLOCKSTORE`, 300-KRN-0001).
- **Asked of the shell:** to start a program in a domain the owner names, with that domain's client in `SLOT_BLOCKSTORE` in place of the shell's. With a read-only request (`REQUEST_BLOCKSTORE_READ`), the domain's client has the get badge alone. The program then holds no client of the volume or of any other domain.
  - The form is APP's to choose, for instance `run -d <domain> <program>`.
  - A domain that is not the shell's, or not live, is refused with the store's error.
- **Why:** an agent (260) is to hold its own memory only (312's plan, "a memory domain is a capability, and an agent holds its own only"). Today no program can be started that way, so no QEMU run shows it.
- **Then STO** runs `blocks` started so as the stand-in agent in the `store` suite: its journal, index and assertions in its domain, the volume's names and another domain's out of its reach, and the domain forgotten by the owner.

- **Seen:** `wm` logs `STARTED fm PID … WITH window,files,sysinfo,shell WITHOUT clipboard`, and the same for `console`.
- **Why, read from the code** (no trace was taken):
  - The shell lends a window manager a copy that may badge (`clipctl::Clip::lend(true)`) through `loader::grant`.
  - The IDL runtime sends every capability without `CAP_BADGE` (`libmind/src/idl/wire.rs`, `PASSED`, [000-KRN-0073](../issues-done/000-KRN-0073-a-badge-set-only-with-the-right-to-set-it.done)), so `wm` receives an unbadged client without the right.
  - The kernel then refuses `wm`'s `mint_badged` (its manager copy and each program's copy).
  - The shell's own copies are unaffected: `init` gives it the right by spawn, not on the wire.
- **What runs meanwhile:** `wm`'s programs keep their own copy buffers, the fallback 000-APP-0032 names. 0235's checks read `wm`'s lent list before `WITHOUT` and do not check the clipboard.
- **Two ways out:**
  1. **Recommended, keeping 0073's rule:** the service mints programs' copies itself, as `blockstore` mints its domains' clients.
     - KRN: `init` gives `clipboard` its server endpoint with `CAP_BADGE`, as `blockstore` and `storefs` have theirs.
     - APP: `clipboard.wit` 1.1 adds a call answered on a `BADGE_MANAGER` copy that returns a client badged `BADGE_PROGRAM`. The shell lends `wm` a copy badged `BADGE_MANAGER`, which travels on the wire as any badged copy does. `wm` names the window in front with it and asks the service for each program's copy.
     - The request 0235 carried already says "a manager's (`BADGE_MANAGER`) for itself and for a window manager it starts".
  2. **A launch that keeps the right:** a loader call (or a raw message to `grant`) that passes `CAP_BADGE`, used by the shell for a window manager alone.
     - It makes an exception to 0073's stated guarantee ("the IDL runtime passes every capability without the right"), and `docs/profile` would say so.
     - KRN would make it; APP would change the shell's one call.
- **Asked of APP:** which way. For the first, a line here or in `KRN/` when `clipboard.wit` 1.1 is ready, and KRN gives the service its endpoint with `CAP_BADGE` in the same round.
