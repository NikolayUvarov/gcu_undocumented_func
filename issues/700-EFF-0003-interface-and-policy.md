# 700-EFF-0003 — The interface between the two services, the owner's policy and the audit record

**Type:** design (interface) · **Owner:** `EFF` track (open) · **Priority:** P1 · **Status:** open · **Blocked by:** — · **Main task:** [700](700-effector-agent.md) · **Constitution:** MC-2.3, MC-3.4, MC-3.5, MC-3.8, MC-3.11, MC-10.3, MC-10.6, MC-10.7, MC-11.11, MC-7.5

## Problem

- **Separate services.** The network-facing `effector` must not hold the authorities that act on the machine (MC-11.11). Those sit in `effector_gw`, which must decide each request by a policy the owner set, not by what the server asked for (MC-3.8, MC-3.11).
- **Not written yet.** None of these three pieces exists:
  - the typed requests between the two services;
  - the policy's form;
  - the audit record.

## Plan

- **`idl/effector.wit` 1.0** (`docs/idl/README.md` rules, generated by `scripts/mind_idl.py`). Each request carries:
  - the server's command ID;
  - the initiator and reason as the server gave them;
  - a deadline.
- **Its typed calls:**
  - `status` (for the heartbeat);
  - `service-control`;
  - `collect-log`;
  - `collect-file` (in chunks);
  - `deliver-file` (begin, chunk, commit, abort);
  - `package` (begin, chunk, verify, install, uninstall);
  - `update-check`;
  - `reboot`;
  - `cancel`.
- **Typed results** say `completed`, `failed`, `denied`, `cancelled` or `unknown` with a reason. All lengths are bounded.
- **The policy:** `data/effector/policy`, a text file the owner writes with the shell (requests-APP). Its contents:
  - whether the agent runs at all;
  - which services may be started, stopped or restarted;
  - which log sources and which file roots may leave the machine;
  - the delivery root;
  - whether packages may be installed, and the package keys trusted;
  - whether system updates may be checked or applied;
  - whether a reboot is allowed.
  - Anything not named is denied. The file is read at start and on the owner's command, never on the server's.
- **The audit record:**
  - one line per request, written before the reply: time, command ID, initiator, reason, typed request, decision, result;
  - it goes to `logd` and to a bounded file `data/effector/audit` that rotates;
  - the agent's own token and keys never appear in it (MC-10.3);
  - a failed write stops the request (MC-10.6).
- **The threat analysis** goes in `docs/effector/README.md`:
  - **what each service holds:** its authorities and what it can reach;
  - **if `effector` is taken over:** it can ask for anything, and only the policy limits what is done;
  - **if the server is taken over:** the same, within the policy;
  - **what leaves the machine.**

## Acceptance criteria

- `idl/effector.wit` and the generated `libmind` file are committed, and `tests/idl_test.py --check` passes.
- The policy grammar is documented. A host test checks:
  - the parser on valid files, on files with unknown keys, and on a file too large;
  - the decision table, including "not named means denied".
- The threat analysis names each authority of both services.
