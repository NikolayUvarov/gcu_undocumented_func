# Удалённые машины для сборки и тестов через Effector

**Версия:** 1.3 (2026-10-23): продление брони продлевает время её команды, а после окончания брони у прогона есть ещё час (правило 3); 1.2 (2026-10-23): аренда брони — не предел; операция пока заканчивается по своему `timeout_seconds`, пока сервис не перестанет обрывать команды; работа частями по часу-два, слово мейнтейнера (правило 3); 1.1 (2026-10-23): 1.0 (2026-10-10) · **Для кого:** все агенты и люди, работающие над MIND Core ([AGENTS.md](../AGENTS.md)) · **Конституция:** [v1.6](../constitution/RU/MIND_CORE_Constitution_v1.6.md) MC-12.1, MC-12.9 (доказательство называет свою конфигурацию) · **English version:** [effector.md](effector.md) (основной текст; русский поддерживается в соответствии с ним)

Сопровождающий даёт агентам настоящие машины для сборок и тестов через **Effector** (Эффектор) — службу, которая выполняет команды на зарегистрированных компьютерах.

- **Каждую машину делят несколько агентов.** Этот документ говорит, как работать на них, не мешая друг другу.
- **Основное описание службы** — её собственное:
  - справка для агентов, <https://hesere.uz/effector/ahelp>;
  - API, `GET https://hesere.uz/effector/api/openapi.json` (с ключом).
- **Прочитайте их первыми.** Если они расходятся с этим документом, то в том, как вызывать службу, правы они, а в том, как агенты MIND делят машины, прав этот документ.

## 2. Ключ

- **Где взять ключ.** Попросите у сопровождающего ключ API для своей сессии. Храните его только в файле в личном каталоге сессии (права 0600) и никогда в репозитории.
- **Как передавать.** Только в заголовке `X-API-Key`.
- **Где ключа быть не должно:** в URL, в командной строке (её видно в списке процессов), в журнале, коммите, задаче или ответе. Не печатайте его для проверки: `GET /api/v1/api-key` скажет, действует ли он.
- **Ключ на сессию**, чтобы сопровождающий видел, чья операция чья.

Минимальный клиент на Python (только стандартная библиотека):

```python
import json, os, time, urllib.request

BASE = "https://hesere.uz/effector"
KEY = open(os.environ["EFFECTOR_KEY_FILE"]).read().strip()  # файл 0600 в вашем личном каталоге

def call(method, path, body=None):
    data = json.dumps(body).encode() if body is not None else None
    request = urllib.request.Request(BASE + path, data=data, method=method,
                                     headers={"X-API-Key": KEY, "Content-Type": "application/json"})
    with urllib.request.urlopen(request, timeout=60) as reply:
        return json.load(reply)
```

## 3. Постановка работы

Операция выполняет один скрипт оболочки на машине от имени пользователя:

```python
script = open("build_and_test.sh").read()   # POSIX sh; вывод короткий (хвосты журналов)
op = call("POST", "/api/v1/operations", {
    "agent_id": "PCU_585240b00e8a", "kind": "exec", "run_as": "un", "command": script,
    "timeout_seconds": 3600,             # собственный срок этой операции, его выбирает отправитель (API принимает от 1 до 3600)
    "sequential": True,                  # долгая или тяжёлая работа ждёт в очереди машины
    "queue_ttl_seconds": 6 * 3600,       # сколько она может ждать за работой других агентов
    "idempotency_key": "KRN-351-KRN-0057-x86-20261010T0400",
    "reason": "KRN 351-KRN-0057: the x86 group on QEMU 8.2.2"})
FINAL = {"completed", "failed", "timeout", "expired", "cancelled", "rollback",
         "run_as_unavailable", "interactive_session_unavailable", "denied"}
while op["status"] not in FINAL:
    time.sleep(5)
    op = call("GET", f"/api/v1/operations?id={op['id']}")
    # пока ждёт: op["queue_position"], 1 — следующая
print(op["status"], op.get("result", {}).get("exit_code"), op.get("result", {}).get("stdout", "")[-3000:])
```

### Выбор машины (сопровождающий, 2026-10-14)

Машины появляются, уходят и меняются: сопровождающий добавляет их и может перевести агента в службу (тогда меняется его ID), а очереди занимают другие треки. Поэтому машину выбирайте каждый раз заново:

- **Когда.** Перед каждой порцией долгой работы (сборка, набор, часть гейта), и ещё раз, если порция ждёт в очереди или идёт заметно медленнее обычного.
- **Как.**
  1. `GET /api/v1/endpoints`: у каждой машины `online`, `parallel_limit`, `occupied_queues` и `free_slots`.
  2. `GET /api/v1/operations?agent_id=…&status=active` у кандидатов: чья работа там стоит в очереди или идёт и как давно.
  3. Раздел 1: что есть на каждой машине (всё для aarch64, пакеты CI или другие), какого пользователя указывать и насколько она быстра.
- **Какую.** Ту, где есть всё нужное работе и больше всего места для неё:
  - сначала свободная очередь: работа в очереди за чужими треками обходится дороже, чем более медленная, но свободная машина;
  - из свободных — более быстрая: сегодня `un-rizen-service` (4 очереди), затем `acc-1` и `acc-2` (по 2 очереди, группы x86 идут так же быстро, как на un-rizen), затем `i9` (5 очередей, но общая и под WSL), затем PCU (работа QEMU там идёт последовательно), затем `DESKTOP-i7-930-wsl-u24`;
  - машину, уже нагруженную группами QEMU других треков, — только если свободной нет: под нагрузкой группа не укладывается в свои тайм-ауты, и её провал ничего не говорит об изменении (2026-10-14 на i9 при нагрузке 39 группа, которая идёт 16 минут, шла больше часа);
  - части гейта могут идти на разных машинах, а все группы должны пройти на одном коммите.
- **Машина, которой нет в разделе 1,** настроена так, как никто не описал: опишите её там вместе с сопровождающим, прежде чем считать её прогоны свидетельством.
- **Свою операцию, которая долго ждёт,** можно отменить по её ID (правило 7) и поставить туда, где есть место.
- **В отчёте** сказано, где шла каждая часть (раздел 4).

### Правила совместной работы

1. **Долгая или тяжёлая работа идёт по одной операции на трек.** Это сборка, тесты на хосте, набор QEMU или группа гейта.
   - Машина выполняет одновременно столько операций, сколько у неё очередей: `parallel_limit` в `GET /api/v1/endpoints`, рядом `occupied_queues` и `free_slots`. Сопровождающий задаёт его на странице Agents по числу ядер машины: двум группам QEMU сразу нужно примерно вдвое больше потоков, а группа на 16 CPU занимает 16.
   - **Одна очередь** (`parallel_limit` 1): укажите `"sequential": true`. Все такие операции одной машины, от какого бы агента они ни пришли, ждут в одной очереди «первым пришёл — первым выполнен» и идут по одной.
   - **У PCU** (4 CPU) с 2026-10-12 `parallel_limit` 3, но группы QEMU и сборки на нём по-прежнему идут последовательно. 2026-10-12 группы двух треков шли там одновременно обычными операциями: нагрузка поднялась до 15–20, и группы aarch64 трека ядра не уложились во время. Остальные очереди PCU — для коротких лёгких операций.
   - **У `un-rizen-service`** (16 потоков) `parallel_limit` 4, **для всех треков и агентов** (сопровождающий, 2026-10-14). Это машина для сборок, тестов на хосте, групп QEMU и гейтов, x86 и aarch64:
     - долгую работу ставьте туда обычными операциями, никогда не `"sequential"`: последовательная линия — одна очередь, и три остались бы без дела;
     - каждый трек ведёт там одну долгую операцию за раз, так что строить и тестировать могут четыре трека сразу;
     - вторую очередь трек может занять, только пока свободны две, и из второго своего клона со своим `TMPDIR` (`/home/un/mind-core/<TRK>-2/`, `/tmp/mind-<TRK>-2`): две группы в одном клоне или одном `TMPDIR` затирают друг другу образы и журналы;
     - группа QEMU занимает примерно столько потоков, сколько CPU у её гостя (у большинства групп четыре), так что четыре помещаются; группа на 16 CPU занимает всю машину, пока идёт, и остальные группы тогда идут медленнее.
     - группы x86 «boot, display, network, TLS», «keys, shell, tools» и «files and block writes» идут только в первой полосе, без второй вашей группы рядом: две сразу не укладывались в короткие ожидания (раздел 1, замеры 2026-10-14).
   - **Несколько очередей:** долгую работу ставьте обычными операциями (без `"sequential"`) и по одной: следующую — только когда кончилась прежняя. Работа сверх предела ждёт свободной очереди. Последовательные операции по-прежнему делят одну линию, так что трек, отметивший свою работу как последовательную, ждёт за последовательной работой других.
   - Временные файлы каждый трек держит в своём `TMPDIR` (правило 4), какой бы ни была очередь.
   - `queue_ttl_seconds` выбирайте по той очереди, которую видите (`GET /api/v1/operations?agent_id=…&status=active`). Ожидание входит в этот срок, и операция, прождавшая дольше, истекает.
   - Короткие проверки только на чтение (версии, свободное место, хвост журнала) ставятся без `"sequential"`. Очередь они всё равно занимают: при одной очереди ждут текущую операцию.
2. **Ничто не переживает свою операцию.** Никаких `nohup`, `&`, `setsid`, `screen`, `tmux` или `systemd-run` для работы. Отсоединённая работа идёт мимо очереди и сталкивается со сборкой или тестом следующего агента.
3. **Время** (мейнтейнер, 2026-10-23).
   - **1–60 минут брони очереди — это аренда, а не предел для работы.** Она нужна для того, чтобы забытая бронь снялась сама. Продлевайте её столько раз, сколько нужно работе: сервис не ограничивает ни общее время, ни число продлений.
   - **Продление брони продлевает и время выполнения команды, отправленной под ней** (с заголовками сессии и PIN брони, справка сервиса), а после окончания брони у прогона есть ещё час, чтобы закончиться. Поэтому долгий гейт под продлеваемой бронью не обрывается.
   - **Операция, отправленная без брони, заканчивается по своему `timeout_seconds`** (API принимает от 1 до 3600): сервер завершает её с `agent did not acknowledge the operation before timeout_seconds elapsed`.
   - **Работу всё равно делите на части примерно по часу, не больше двух:** например, по одной группе QEMU или одной сборке, друг за другом. На медленной машине группа, которой нужно больше, идёт на более быструю или делится мельче.
   - **`timeout` говорит, что часть не уложилась в своё время, а не что изменение неверно.** Так о нём и пишите: какой `timeout_seconds` был у операции и что она успела сделать.
4. **У каждого трека свой каталог:** `/home/un/mind-core/<TRK>/` (например `/home/un/mind-core/NET/`), со своим клоном и своими каталогами `target/`.
   - Никогда не собирайте в чужом каталоге, не чистите и не меняйте его.
   - Клон трека ядра пока лежит в `/home/un/mind-core/gcu_undocumented_func` и переезжает в `KRN/`.
   - **Каждая операция экспортирует `TMPDIR=/tmp/mind-<TRK>`** (сначала `mkdir -p`). Тогда `scripts/ci_local.sh`, тестовые программы, варианты ядра, журналы и файлы наборов QEMU пишутся туда ([000-KRN-0092](../issues-done/000-KRN-0092-two-tracks-test-side-by-side.done)), и прогоны двух треков на одной машине не делят ни файлов, ни блокировки. Путь держите коротким: наборы кладут туда управляющие сокеты QEMU, а путь Unix-сокета должен быть короче 108 байт. Тест или скрипт, который всё ещё пишет в постоянный путь под `/tmp`, — ошибка: сообщите о ней треку-владельцу.
5. **Называйте свои операции.**
   - `idempotency_key` начинается с кода вашего трека и уникален для каждой новой постановки.
   - `reason` называет трек, задачу и что выполняется (`"STO 300-STO-0002: the store suite on x86"`). Сопровождающий читает его на панели.
6. **Повтор без дублей.**
   - Оборвавшийся вызов мог успеть поставить операцию. Прежде чем ставить снова, посмотрите активные операции и, если ваша там, дождитесь её.
   - Повторяя постановку, в которой не уверены, используйте тот же `idempotency_key`.
7. **Отменяйте только свою операцию, по её ID**: `POST /api/v1/operations/cancel` с `operation_id`, собственным `idempotency_key` и `reason`; без двух последних запрос отклоняется (HTTP 400). Отменять можно и ожидающие, и выполняющиеся операции. Никогда не отменяйте по `agent_id`: так отменится ожидающая работа всех агентов на машине.
8. **Работайте от `un`.**
   - Учётная запись root (`run_as` `service`) — только для изменения машины, о котором попросил сопровождающий. Запишите такое изменение в раздел 6 в том же коммите, что и работу, которой оно понадобилось.
   - Не ставьте, не удаляйте и не обновляйте пакеты, не меняйте `/opt`, `/usr/local` и настройки системы для своего удобства. Спросите сопровождающего.
9. **Никогда не перезагружайте и не выключайте машину** и никогда не трогайте:
   - её сетевые настройки;
   - её пользователей, `ssh` и службу, которая запускает агента Effector;
   - другие её службы и файлы других пользователей.

   Машина без сети недоступна, пока кто-нибудь не подойдёт к ней.
10. **`fast-test` и здесь никогда не собирается и не тестируется** ([AGENTS.md](../AGENTS.md), раздел 4): только своя ветка.
11. **Убирайте за собой.** Удаляйте свои большие результаты, когда они не нужны. Перед большой сборкой посмотрите `df -h /home`.

## 4. Гейты на удалённой машине

- **Гейт очереди посадки** (AGENTS.md, раздел 4, с 2026-10-21) идёт так же. `scripts/land.sh gate` раскладывает все группы `scripts/ci_local.sh --list` по очередям машин и запускает упавшую группу ещё раз, одну. Ключ он берёт только из файла `$EFFECTOR_KEY_FILE` (раздел 2). Очереди называют предустановки: `full`, и `no-i9`, пока i9 нагружен гейтом другого трека; `i9-on-rz`, которой гейтились раунды 34–39, пока i9 был выключен; `wide` с 2026-10-28, где длинные группы x86 идут на `acc-1` и `acc-2`, и `wide-no-i9`, пока i9 занят.
- **Пул** (`--preset pool`, или `pool-no-i9`, пока i9 занят; с 2026-10-29, по просьбе сопровождающего). Ни у одной очереди нет списка.
  - **Очереди:** i9, `acc-1`, `acc-2`, два клона на `un-rizen-service` и PCU. С третьим клоном там группы шли на треть дольше, и `kbench` превысил предел для вызова с ответом (раунд 44).
  - **Что берёт каждая:** освободившись, самую длинную из оставшихся групп, которую может выполнить. Часть host идёт только на `un-rizen-service`, i9 не берёт групп aarch64, PCU берёт только группы aarch64.
  - **Сборки:** очередь собирает образ части, когда впервые берёт её группу.
  - **Оценки** — секунды из таблицы ниже, затем собственные записи гейта о тех же группах; `--dry-run` печатает расписание, которое они дают.
  - **Гейт, запущенный снова** на том же кандидате, даёт каждой очереди те же группы в том же порядке (`$LAND_WORK/gate-<commit>-taken.json`), и Effector отвечает уже готовыми результатами.

### Часть гейта для aarch64 идёт на удалённой машине (решение сопровождающего, 2026-10-10)

- **Где.** На машине из раздела 1, где есть всё для aarch64, выбранной, когда часть начинается (раздел 3, «Выбор машины»): `PCU_585240b00e8a` и, с 2026-10-14, `un-rizen-service`: она быстрее, и очередей у неё четыре (раздел 3, правило 1). Сопровождающий добавляет новые машины; каждая попадает в раздел 1 со своей конфигурацией.
- **Зачем.** На машине агента x86-часть локального гейта идёт около 70 минут, а aarch64-часть — ещё около 65. PCU выполняет группы aarch64 в 1,2–1,6 раза медленнее, но **параллельно** с x86-частью. Тогда гейт длится примерно столько, сколько его более долгая половина, а машина агента занята только x86-частью.
- **Замеры 2026-10-10** (дерево трека ядра 9c843b4, одна группа на операцию, секунды):

| Группа | Машина сессии ядра | PCU |
|---|---|---|
| build (aarch64) | 214 с | 248 с |
| aarch64: boot and fault containment | 90 с | 8 с, не прошла: QEMU падал в `vvfat` (106 с и проходит после 000-KRN-0067) |
| aarch64: programs, shell and four CPUs | 339 с | 394 с |
| aarch64: files, network and TLS | 1121 с | 1819 с |
| aarch64: RAM, ACPI and PCI above 4 GiB | 826 с | 1063 с |
| aarch64: GICv2 with GICv2m | 758 с | 922 с |
| aarch64: NVMe boot disk | 132 с | 187 с |
| aarch64: 16 CPUs | 340 с | 525 с |

- **Как.** Запускайте в клоне своего трека, `/home/un/mind-core/<TRK>/gcu_undocumented_func`, по одной последовательной операции (`"sequential": true`) на шаг; каждая заметно короче часа, отпущенного операции:
  1. **Дерево.** Приведите клон к своей ветке, слитой с `main`, как это сделал бы `--ref`:
     - `git merge --abort; git reset -q --hard`;
     - `git fetch origin`, `git checkout --detach origin/<ваша ветка>`;
     - `git merge --no-edit origin/main`.
  2. **Сборка.** `scripts/ci_local.sh --only aarch64 --group "build (aarch64)"`.
  3. **Группы.** Каждая группа aarch64-части на том же дереве, по операции на группу: `scripts/ci_local.sh --only aarch64 --group "aarch64: programs, shell and four CPUs"` и так далее. Их имена даёт `scripts/ci_local.sh --list --only aarch64`.
  4. **Журналы.** Нужное скопируйте в каталог своего трека в той же операции. Следующий запуск чьего угодно `ci_local.sh` удаляет `/tmp/mind-core-*.log` и переписывает `/tmp/mind-ci-local`.
- **В отчёте** указывается, где шла каждая часть: «x86-часть локально; aarch64-часть на PCU через Effector (Ubuntu 22.04, QEMU 8.2.x с qemu.org, AAVMF 2022.02)». Вместе они составляют один локальный гейт в смысле [AGENTS.md](../AGENTS.md), раздел 4, если все группы обеих частей прошли на одном и том же коммите.
- **Всего около 86 минут на PCU** против 64 на машине сессии ядра, для проходящих групп.
- **«aarch64: boot and fault containment» теперь тоже идёт на PCU** (с 2026-10-11, [000-KRN-0067](../issues-done/000-KRN-0067-the-aarch64-boot-test-on-pcu.done)).
  - Раньше она там не проходила: драйвер `vvfat` в QEMU аварийно завершался, когда гостевая система писала на свой загрузочный том (`fat:rw:`): `handle_renames_and_mkdirs: Assertion 'j < s->mapping.next' failed`.
  - Теперь тест загружается с готовых образов FAT, а `vvfat` обслуживает только подставной диск, открытый только для чтения. На PCU группа прошла за 106 с (cf0283f), на машине сессии ядра тоже.
  - Запускайте её в aarch64-части вместе с остальными группами (шаг 3).

## 5. Если что-то пошло не так

- **`timeout` с «agent did not acknowledge»** не доказывает, что ничего не выполнилось. Посмотрите результат операции и состояние машины, прежде чем повторять.
- **Ошибки HTTP несут `X-Effector-Request-ID`.** Сохраните его, когда сообщаете о проблеме сопровождающему.
- **Машина не отвечает:** скажите сопровождающему. Не пытайтесь восстановить её сами.
