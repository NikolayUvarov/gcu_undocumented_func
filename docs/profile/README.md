## Platform

- x86-64, UEFI (OVMF in QEMU), 1–8 CPUs with the local APIC in xAPIC mode, and in x2APIC mode in the group `x86: x2APIC` (a test kernel switches the boot CPU as firmware would; `normal`, `busy`, `smp`, `isolation`; 211-PRT-0002), no SMT siblings in the tested configuration (`-smp N,cores=N,threads=1`).
- QEMU `pc` machine with IDE, optionally AHCI, xHCI with USB mass storage, AC97; physical machines boot from the USB image but are not part of the evidence.
- **No IOMMU is used.** Every device that can do DMA can read and write all physical memory.
- One node. Up to two VirtIO network cards (QEMU `virtio-net-pci`; one driver instance and one interface per card, issue 105) and an IPv4 stack (`netstack`, DHCP, ICMP, DNS, UDP, TCP) run in ring 3. Flows follow the policy broker (`netpolicy`, `netpolicy.txt` on the boot disk, issue 102): an application reaches only the destinations, term and volume its grant names; the shell's client has the operator's badge and reaches any destination. TLS 1.3 client sessions (`tls`, issue 103) run over a flow the client lends, with server certificates verified against `tlsroots.pem` on the boot disk; random numbers come from RDRAND only (no RDRAND: no TLS and no device key). Network confidentiality and integrity are claimed only for those sessions, not for the stack's other traffic. Network performance and the offload decision: [network.md](network.md).

| MC-3.12 end of initial distribution | met | Bootstrap authority is only `init` ([bootstrap.md](bootstrap.md)). | Article 4 storage | partial | A block store, `blockstore` ([docs/storage](../storage/README.md)), runs at boot over a RAM disk of its own (`ramdisk#1`). Blocks are immutable and named by CIDv1, which names the format's version, the content type and the hash algorithm; unknown formats are refused (MC-4.2, 4.13). The log is append-only: nothing stored is overwritten. Every block read is checked against its CID (MC-4.8). Objects larger than a block are a Merkle-DAG whose nodes are checked against their type. A name's current version changes only by compare-and-swap, and only to a root whose blocks are all stored (MC-4.3, 4.4). Up to 8 names change at once through a commit, all or none: every change is checked before one record with one digest is written, a damaged or torn commit changes no name, requests are served one at a time and `snapshot` reads several names at one point; the durability is a publication's (MC-4.10). Reading, storing and publishing are separate rights by badge (MC-4.7, 4.11). Retention policy (MC-4.5, 4.11, B.3): a name keeps its newest 4 versions, each record linking the root before it, and each kept version retains its object; removing a name writes a version without a root, which ends what the name retains, and its data goes only when nothing else retains it (MC-4.8); a pin retains its object until its owner (the client's badge) ends it; what an owner's names and pins retain is charged to it, each root once, and bounded by a quota (three quarters of the medium); a block nothing retains is kept for a 60 s lease after its last put or a mount, for writes in progress. A collection marks what names and pins reach, refuses if an object lacks a block, frees the rest crash-safely and reuses the room; it runs when a write finds no room, or on request. Evidence: `store` suite (an object gets the independent reference's root and reads back, a file round trip, compare-and-swap, an incomplete root refused, a full medium refused, the store found again after a restart, room freed by a collection once leases end and written again, a name's earlier version kept, history, quota refusals, a pin, a removal found again after a restart; commits of two names, refused whole for a stale version or a missing root, found whole after a restart); `storefaults` suite (damage injected from the host into the medium's bytes in guest RAM: a corrupt chunk refused when read and when mounting and repaired by a put, a collection refused meanwhile, a damaged header losing its record alone, a damaged name record counted and the version before it current, a damaged commit changing no name; a killed store restarted, and an unmountable medium answered with the reason while the rest of the system goes on); host tests `tests/cid_host.rs`, `dag_host.rs`, `blockstore_host.rs`. Not met: durability beyond a reset (the medium is RAM, so a publication is durable only to that level, MC-4.4); pins with a term of their own, and quotas granted per owner rather than one fixed share (MC-4.11, B.3); owners apart from badges; obligations to consumers; copies on independent media and repair (MC-4.8); commits across stores and snapshots held across requests (MC-4.10); semantic links and indexes (MC-4.6). Damage on the platform is injected by the test into RAM, not caused by a device. Refusals by badge: a client that may only read is refused `put` and `publish` on the platform (`store` suite); a client that may only store exists nowhere, and its refused read is host-tested only. FAT volumes are external media written in place, without a journal ([threat-model.md](threat-model.md)). |
| MC-5.1–5.5 budgets | partial | Scheduling contexts (C7): a CPU budget per period, enforced at the 10 ms tick, set by the lifecycle owner or process control (`SCHED_SET`); two bands — `init` and services run before applications, so the supervisor's reserve survives application overload. | MC-6.4–6.9 supervision | partial | `init` is the lifecycle owner of every service: the kernel sends it exit notices (`TASK_WATCH`), it restarts a failed service at most 3 times in 60 s and then quarantines it until an explicit `RUN`. Sends queued for a dead server fail with `ERR_PEER` instead of reaching the next instance; clients tell instances apart by the server PID in replies. Without `init` the system halts. Evidence: `services` suite (restart, budget, quarantine, halt), `isolation` case `f` (queued send fenced). Before a driver restarts, its device is stopped (`DEVICE_STATE`) and its DMA region cleared (MC-6.3, `ahci` and `net` suites). The block client re-attaches to a new driver instance and repeats only idempotent reads (MC-6.6). The supervisor does not depend on memory applications can exhaust (MC-6.5, issue 169): `init` keeps 32 MiB of the frame pool for the system band (`MEMORY_RESERVE`), and application-band allocations stop above it. Evidence: `memory` suite (applications that take all they can leave the reserve; `rtc` killed meanwhile restarts and serves). The window broker, a service, allocates application windows' surfaces and can draw on the reserve within its own quota; the reserve is free memory, not a contiguous block. The storage service is outside the boot path (MC-6.8, B.4): everything the system needs to start or to restart `blockstore` is on the boot volume, and nothing starts from the store. Not done: idempotency rules for other protocols, lifecycle owners of applications beyond loader's accounting. |
| MC-6.10–6.12 checkpoints, rebinding, fencing | partial | A checkpoint contract format and protocol, version 1 ([checkpoints.md](../storage/checkpoints.md), `mind::checkpoint`, 306). A manifest records the contract and its version, the schema, the instance's epoch, the consistency point, the state's root, resources by logical name, authorities as text and an effect journal. It is saved with the state under two names in one commit, so a save from a stale epoch is refused (fencing, MC-6.12). A restore checks the contract, schema, epoch and roots; rights come from the instance's current grants, never from the checkpoint (MC-6.11); effects begun and not recorded come back pending for reconciliation (B.4). | Article 9 boot and update | partial | Signed boot volumes ([docs/update](../update/README.md), 350). The build writes a manifest of every shipped file (size, SHA-256, the authorities a program asks for, which grant nothing: MC-3.11) and its build inputs (commit, toolchain, a digest of every `Cargo.lock`), and signs it with Ed25519. The bootloader checks the signature against the public key built into it, then the kernel and every boot service against the manifest, before it loads anything. A change, another key's signature or a missing signature stops the boot with the file named (MC-9.1, 9.2). It prints a launch record (the manifest's digest, the key, the images checked) on the serial line. Trust model: the anchor is the bootloader's built-in key; on a machine without Secure Boot nothing checks the bootloader, so an attacker who can write the whole boot volume is not stopped. Secure Boot with the project's own keys ([secure-boot.md](../update/secure-boot.md), 351-UPD-0012) closes that in QEMU: with our PK, KEK and db enrolled in OVMF, only the bootloader signed with our db key runs, and one whose hash is in dbx does not (`tests/secure_boot_smoke.py`); it has not run on real hardware. The updater ([updater.md](../update/updater.md), 351-UPD-0007) checks a release channel with the release key built into it and each manifest with the boot key, stages the newer release's boot files in the slot that did not boot (each checked by size and SHA-256 on the disk), writes the trial record and asks init to restart, and writes the confirmed record once the trial outlives the kernel's deadline; refused releases (expired, badly signed, older, a changed file) write no record (the `update` check, x86 and aarch64). The zone it may write is built in `vfs_server` (351-UPD-0008, [slots.md](../update/slots.md)): on a system booted from a slot, a client with the update badge may change only the slot that did not boot and write the two boot records whole, in place (one sector, flushed); the running slot, `EFI/` and everything else stay read-only to it, and a system booted from the volume's root has no zone. Evidence: `tests/vfs_zone_host.rs` (every badge's zone, a record write that changes one sector) and the `boot` suite (the zone named for the slot that did not boot, x86 and aarch64); init gives the badge to the updater alone (351-KRN-0022), and the updater writes through it in the `update` check. The boot volume (211-KRN-0012): the bootloader names the partition it was loaded from (from the firmware's device path) in `BootInfo`, and `vfs_server` mounts only the FAT volume on that partition holding the manifest the bootloader verified, or says none is there; a kernel and a bootloader of different ABI versions stop in the kernel with the reason. Builds without a release key use a public test key and say so. Reproducible builds (MC-9.5, 9.7): two builds of one commit at the same checkout path are byte-identical (`scripts/reproducible.sh`, local gate); the checkout path is a recorded condition, since builds at different paths differ. Evidence: `boot` suite (a signed volume boots; a changed kernel or service, a changed manifest, another key and no signature refused; slots: a trial and its confirmation, an unconfirmed trial's fallback, a damaged slot, a torn record; a decoy disk ahead of the boot disk; a bootloader of another ABI; with `--trial-kernel` a confirmed trial past its deadline and an unconfirmed one restarted and fallen back; aarch64: the decoy is not mounted), every suite boots from a signed volume, `tests/manifest_test.py`, `tests/boot_slots_host.rs`. The launch record (the manifest's digest, the key, whether it is the test key, the images checked) reaches every task in `BootInfo` and the system log through init (350-KRN-0023), the same as the serial line. The firmware's boot variables (351-KRN-0027, 351-KRN-0028): on x86 and aarch64 the kernel reads and writes UEFI variables through the firmware's runtime services for a holder of the firmware privilege, which the shell lends to a program only when the user allows it; with OVMF and AAVMF, `efivar bootnext` to the firmware's shell boots that shell once and the next boot is MIND Core again (`boot` suite, `efivar` suite on aarch64); a `dbx` update signed with our KEK, appended from the system with `efivar append dbx`, makes OVMF's Secure Boot build refuse the bootloader it revokes at the next boot, and an unsigned one is refused (`tests/dbx_update_smoke.py`, x86, 351-KRN-0028); the updater's grant of it waits for 351-KRN-0022. Not met: verification of applications by the loader, a tool that shows the launch record, Secure Boot on real hardware and on aarch64, key roles and rotation (MC-9.6), a caller of the updater's interface (it acts only by its automatic policy), images built with slots (351-UPD-0016), authenticated variable writes on aarch64, applications in the slots, rollback protection (MC-9.3, 9.4). |

## Memory transfers (Appendix B.2)

Every memory capability a service hands to another task, and its mode (MC-2.6). `MEM_SHARE` makes a capability for a block of the caller's own heap; the modes below say what the receiver gets and when its access ends.

| Transfer | Mode | Receiver's access | Ends |
|---|---|---|---|
| MIND IDL buffer calls (`vfs`, `tts`, `loader`, `init`: `wire::call_buffer`) | LEASE, read-write | the server copies the request into private memory before decoding and writes the reply | `CAP_REVOKE` by the client before it reads the reply |
| `audio.play` (`mind::audio`) | LEASE, read-only | `audio_gw` copies the PCM into its DMA ring | `CAP_REVOKE` after the reply |
| `audio.record-read` | LEASE, read-write | `audio_gw` writes captured samples | `CAP_REVOKE` before the client reads them |
| `video.read` (`camera`) | LEASE, read-write | `video_gw` writes one frame | `CAP_REVOKE` before the client reads it |
| `block.attach` (`vfs_server` → `ata`, `ahci`, `usb_storage`) | **SHARE_RW** adapter | the driver writes sector data during `read` calls; `vfs_server` copies it into its private cache right after each reply and parses only that copy (the private-copy condition of MC-2.6) | `CAP_REVOKE` on re-attach to a restarted driver and when the device is closed |
| `usb.attach` (`usb_storage`, `usb_hid` → `usb_host`, issue 164) | **SHARE_RW** adapter | `usb_host` writes interface descriptions, control replies, bulk data and interrupt reports into the class driver's buffer during calls, and reads the data the driver puts there to send; the class driver copies data out after each reply. One buffer per badge; a new one replaces it and frees the old client's interfaces | `CAP_REVOKE` by the class driver before it attaches again, and when it ends |
| Task screens → `compositor` (kernel, `COMPOSITOR_PULL`) | **SHARE_RW** adapter, read-only for the compositor | the owner keeps drawing while the compositor copies the pixels into its shadow buffer and the framebuffer; pixels have no structure to validate, so a torn frame is the only effect (display fences: track G) | the next focus change replaces the capability |
| `net.attach` (`netstack` → `virtio_net`, the frame ring, issue 107) | **SHARE_RW** adapter | both sides write their own counters and slots: the stack queues frames to send, the driver queues received frames; each side copies a frame out of its slot before using it, and checks every counter and length it reads (a slot with an impossible length is skipped; a counter more than the ring's size ahead is ignored) | `CAP_REVOKE` by the stack when it lends a new ring; the driver drops the ring when the stack's task ends or stops kicking for a second |
| `window.surface` (`windows` → a program and its window manager, issue 157) | **SHARE_RW** adapter, memory of the broker | the program draws and queues nothing but its content and title; the manager copies the content out (after `mind::window::Surface::check`: kind and size within the memory) and writes only the requested size, the state and input events; neither can revoke the other's lease, since both come from separate children of the broker's capability | the window's end (`CAP_REVOKE` of the whole surface); the manager's lease also when it detaches or ends |
| `ping` → `pong` (demo) | LEASE, read-only | `pong` reads the text | `CAP_REVOKE` after the reply |
| `SPAWN` image (`loader`) | not transferred | the kernel copies the image during the call | the capability is dropped after `SPAWN` |
| Driver DMA regions (`init` → drivers) | owned by the driver | `PLATFORM_CAP` DMA region, cleared by `init` before a restart | the driver's exit |

`SHARE_RW` is used only by the four adapters above. Not claimed: the end of a lease bounds the receiver's access through its mappings, not what it copied while it held them.
