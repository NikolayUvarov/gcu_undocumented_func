# Ключи обновлений: их жизненный цикл и порядок действий при компрометации

**Версия:** 0.1 (2026-11-13) · **Трек:** `UPD`, задача [351-UPD-0031](../../issues/351-UPD-0031-key-lifecycle-and-compromise-protocol.md) · **Конституция:** MC-9.4, 9.5, 9.6, 11.9 · English: [keys.md](keys.md)

Этот документ даёт для каждого ключа, который ручается за обновление:
- его жизненный цикл: создание, назначение, хранение, использование, смену, отзыв и уничтожение (MC-9.6);
- что делать, когда он скомпрометирован.

Форматы и проверки описаны в [publishing_RU.md](publishing_RU.md) (файл ключей, каналы, метки времени, распоряжения восстановления), [README.md](README.md) и [slots_RU.md](slots_RU.md) (загрузчик) и [updater_RU.md](updater_RU.md) (устройство). Каждая процедура называет свою команду и тест, который показывает её сторону на устройстве.

Тесты — свидетельство, а не доказательство (MC-12.2). Шаги, которые делают люди (где зерно создают и хранят, когда уничтожают), — процедуры, которых требует этот документ; ни один тест не показывает, что их выполнили (MC-12.3).

## Ключи

| Роль | Подписывает | Порог | Кто держит, где хранится | Встроен |
|---|---|---|---|---|
| `root` | файлы ключей (`keys/<версия>`): версию, следующую за своей | порог роли, например 2 из 3 | каждый ключ — у отдельного человека, вне сети, на съёмных носителях, хранимых порознь | первый набор, в загрузчик и программу обновления (`$MIND_ROOT_KEYS`) |
| `release` | файлы каналов (`channels/<имя>`) | порог роли | публикующий, на машине, с которой публикует (`$MIND_RELEASE_KEY`) | нет |
| `timestamp` | файлы меток времени (`timestamps/<имя>`), обновляемые не реже раза в день | порог роли | сервер публикации, который обновляет их сам (`$MIND_TIMESTAMP_KEY`) | нет |
| `boot` | загрузочные манифесты (`MANIFEST.SIG`) | 1: манифест несёт одну подпись | тот, кто собирает выпуск, на машине сборки (`$MIND_BOOT_SIGNING_KEY`) | нет: его называет файл ключей, загрузчик берёт его из файла ключей слота (351-UPD-0029) |
| `recovery` | распоряжения восстановления (`recovery/<имя>`) | порог роли | отдельно от ключа выпусков, вне сети (`$MIND_RECOVERY_KEY`) | нет |
| тестовые ключи | то же, для тестов | как говорит тестовый файл ключей | кто угодно: выведены из открытого текста в `scripts/sign_manifest.py` и `scripts/release.py` | тестовый корневой набор, когда `$MIND_ROOT_KEYS` не задан |
| Secure Boot `PK`, `KEK`, `db` | загрузчик, для прошивки | — | порознь, как сказано в [secure-boot_RU.md](secure-boot_RU.md) (351-UPD-0012) | записаны в прошивку |

- **Ключ — это зерно:** 32 байта в 64 шестнадцатеричных цифрах, в файле вне репозитория. Инструменты читают его из файла, названного переменной окружения или аргументом, но никогда из самой командной строки (MC-11.9).
- **Один ключ — одна роль.** Ключ в двух ролях превращает одну компрометацию в две. `release.py keys make` этого не запрещает; проверяет тот, кто составляет файл ключей.
- **Устройство не держит ключа, подписывающего обновления.** Его собственный ключ, ключ `keystore`, подписывает только за само устройство: TLS и SSH ([docs/profile/tcb.md](../profile/tcb.md)). Обновление проверяется одними открытыми ключами.

## Жизненный цикл

### Создание и назначение

- **Зерно.** Инструменты зёрен не создают. Зерно создают на машине, которая будет его хранить, из её источника случайности, например `python3 -c "import secrets; print(secrets.token_hex(32))" > /media/root1.seed`. Машина корневого ключа не подключена к сети, пока зерно существует.
- **Корневой набор:** `release.py keys root SEED… --threshold T > root.pub` даёт открытый файл. С ним собираются загрузчик и программа обновления (`$MIND_ROOT_KEYS`). Тест: `tests/release_test.py` (`keys root`); каждый набор QEMU загружается под тестовым набором.
- **Файл ключей:** `release.py keys make FILE --version 1 --role boot=…:1 --role recovery=… --role release=… --role root=…:T --role timestamp=…` назначает каждой роли её открытые ключи и порог. Затем файл подписывают по одному корневому ключу, каждый на машине этого ключа (`keys sign FILE SEED`). Его проверяют (`keys check FILE --root root.pub`) и публикуют (`keys publish FILE DEST --root root.pub`). Тесты:
  - `tests/release_test.py`: составление, подпись, проверка, публикация, порог;
  - `tests/release_host.rs`: форма и подсчёт подписей;
  - набор QEMU `update`: файл ключей, который подписал лишь один из двух корневых ключей, отвергается, и запись не пишется.

### Хранение и использование

- **Корневые ключи:** хранятся вне сети, каждый отдельно от других. Используются только командой `keys sign`, на своей машине, для новой версии файла ключей.
- **Ключ выпусков:** использует `release.py publish` после того, как `stage` проверил манифесты сборки.
- **Ключ меток времени:** на сервере публикации, его использует `release.py timestamp` по таймеру там. Он не может изменить то, что говорит канал, только подтвердить, что канал действует ([publishing_RU.md](publishing_RU.md)). Тест: набор QEMU `update` обновляет метку без ключа выпусков.
- **Загрузочный ключ:** использует `sign_manifest.py`, когда сборка подписывает том. `sign_manifest.py` отказывает настоящему загрузочному ключу, которого не называет файл ключей из `$MIND_KEYS`. Тесты: `tests/manifest_test.py`; каждый набор QEMU загружает подписанный том.
- **Ключ восстановления:** использует только `release.py recover`, для распоряжения вернуться. Тест: набор QEMU `update-recovery` (распоряжение, подписанное ключом выпусков, отвергается; подписанное ключом восстановления применяется один раз).

### Смена и отзыв

Ключ заменяют или отзывают следующей версией файла ключей, подписанной порогом текущего корня и порогом своего собственного ([publishing_RU.md](publishing_RU.md), «Смена и отзыв ключа»). Тело этой версии пишут две команды:
- `release.py keys rotate FILE ROLE OUT --key K… --threshold T`;
- `release.py keys revoke FILE KEY OUT`, которая не даёт оставить роль с ключами меньше порога.

Затем тело подписывают и публикуют, как выше. Что делает каждое устройство:

| Роль | Что меняется на устройстве | Тест |
|---|---|---|
| `root` | Программа обновления берёт следующую версию, только если её подписали и старый корень, и новый, каждый своим порогом. После этого она доверяет одному новому корню и хранит эту версию в `system/updater/roots`. Загрузчик следует за сменой через `KEYS.1`, `KEYS.2`, … слота. | набор QEMU `update-keys` (версия 3 меняет корень; версия 4, подписанная старым корнем, отвергается); `tests/boot_keys_host.rs` |
| `release` | Канал, который подписал только старый ключ, отвергается. Так же отвергается слот, чей сохранённый канал подписал только он, и он больше не запасной. | набор QEMU `update-keys` |
| `timestamp` | Метка, которую подписал только старый ключ, отвергается, как и подписанная любым ключом, которого роль не называет, а с ней и канал, за который она ручается. | `tests/release_host.rs`; набор QEMU `update` (метка, подписанная ключом выпусков, отвергается) |
| `boot` | Программа обновления кладёт в слот только манифест, подписанный ключом новой роли `boot`, вместе с новым файлом ключей. Когда этот слот подтверждён, записи называют версию файла ключей, и загрузчик отвергает слот с более старым файлом ключей или с манифестом, который загрузочные ключи файла не подписывали. | набор QEMU `updatebootkey` (351-UPD-0029) |
| `recovery` | Распоряжение, которое подписал только старый ключ, отвергается, как и подписанное любым ключом, которого роль не называет. | набор QEMU `update-recovery` (распоряжение, подписанное ключом выпусков, отвергается); `tests/release_host.rs` |

- **После смены — сразу публиковать под новым ключом.** Новый канал, подписанный новым ключом выпусков; для загрузочного ключа — выпуск, подписанный новым ключом. До того устройство держит то, что у него работает.
- **Более низкий файл ключей, поданный снова, отвергается** каждым устройством, которое приняло более высокий. Тест: набор QEMU `update-keys`.
- **Срок файла ключей истекает** (`--days`, по умолчанию год). Устройство после истечения держит то, что у него есть, как и для канала ([updater_RU.md](updater_RU.md), «Метаданные после срока действия»). Обновлять его нужно новой версией до истечения.

### Уничтожение

- **Зерно уничтожают,** когда его ключ сменён и новая версия опубликована: файл и все его копии перезаписывают и удаляют (`shred -u`), а для корневого ключа — и его носитель. Уничтоженным ключом больше нельзя злоупотребить, а устройство ничего нужного не теряет: ему нужны только открытые ключи.
- **Хранятся, а не уничтожаются:** файлы открытых ключей (`root.pub`, история ключей `keys/<версия>`). Устройство проходит историю с версии 1, она нужна и `release.py check` и `bundle`.
- **Ни один тест** не показывает, что зерно уничтожено; это процедура (MC-12.3).

## Порядок действий при компрометации

Тот, у кого скомпрометированный ключ, может подписывать то, что подписывает этот ключ, пока устройства не примут файл ключей без него. Шаги одинаковы для каждой роли:
1. опубликовать следующую версию файла ключей без этого ключа (`keys revoke` или `keys rotate` с новым ключом);
2. опубликовать под новым ключом то, что подписывает эта роль;
3. уничтожить старое зерно.

Различается то, что ключ мог сделать тем временем, и что остаётся после него.

| Роль | Что может её держатель | Что остаётся действительным | Восстановление |
|---|---|---|---|
| `release` | Подписать канал, называющий любой выпуск, который есть на сервере: предложить более старый, не ниже порога, или задержать устройства. Создать выпуск он не может: каждому манифесту нужен загрузочный ключ, каждому каналу — действующая метка времени. | Каждый уже опубликованный выпуск; работающий выпуск устройства и его запасной, чей канал подписан ключом, который называет новый файл | Не затронуто: ключ восстановления — отдельная роль |
| `timestamp` | Держать канал действующим дольше его срока: устройство не видит более нового канала («заморозка»). Изменить то, что называет канал, он не может. | Каждый канал и выпуск | Не затронуто |
| `boot` | Подписать манифест своей сборки. Устройство загрузит её, только если её называет канал, подписанный ключами выпусков. Тот, кто может писать на диск, может положить её в слот. | Выпуски, подписанные другими загрузочными ключами, которые называет новый файл. Когда подтверждён выпуск под новым файлом ключей, загрузчик отвергает слот с более старым файлом ключей. | Не затронуто; распоряжению восстановления нужен выпуск в другом слоте, подписанный действующим загрузочным ключом |
| `recovery` | Вернуть устройства к выпуску, который держит их другой слот, с опущенным порогом, по одному разу на номер распоряжения. | Каждый выпуск; порог снова растёт со следующим подтверждённым минимумом | Сама: сменить её порогом корня |
| `root`, меньше порога | Сам по себе ничего. | Всё | Сменить корень, пока не потеряны другие ключи |
| `root`, на пороге | Подписать следующий файл ключей: все роли, включая корень. Это вся цепочка обновлений. | Начиная с этой версии, ничто подписанное им не отличить от подписанного владельцем | Новые загрузчик и программа обновления, собранные с новым корневым набором и записанные на каждое устройство вручную; устройство, которое приняло файл ключей злоумышленника, не примет ни одного файла владельца |
| тестовые ключи | Что угодно, для кого угодно: они открыты. | Ничего из выпуска: сборка с ними говорит `THE TEST KEY` | Не нужно: выпусков с ними не делают |
| Secure Boot | Подписать загрузчик, который запустит прошивка | Как сказано в [secure-boot_RU.md](secure-boot_RU.md): старый загрузчик отзывается через `dbx` | — |

- **Как устройства узнают:** только из файла ключей, при следующей проверке (`automatic check`, `update check` или пакет через шлюз Effector). Другого списка отзыва нет.
- **Устройство без сети** ничего не узнаёт, пока не достигнет источника. Тем временем срок его метаданных истекает, и после этого оно держит выпуск, который у него работает, ничего не готовит и не применяет (351-UPD-0025, [updater_RU.md](updater_RU.md)). Короткая метка времени ограничивает, как долго канал можно показывать действующим устройству в сети.
- **Восстановление остаётся доступным,** пока не скомпрометирована роль восстановления. Она отдельна от ключей выпусков, меток времени и загрузки, и распоряжению восстановления не нужен ключ выпусков. Оно ведёт только назад, к выпуску, который держит другой слот; его загрузочный ключ и файл ключей должны по-прежнему проходить проверку.
- **Чего смена ключа не отменяет** (MC-9.6, последнее предложение):
  - выпуск, который скомпрометированный ключ дал установить, остаётся установленным, пока его не заменит более новый;
  - то, что этот выпуск сделал, пока работал, остаётся сделанным: прочитанные данные, использованные ключи, отправленные сообщения;
  - выпуск, изменивший саму программу обновления, может отвергнуть то, что придёт следом: такое устройство записывают заново вручную;
  - смена ключа прекращает дальнейшее принятие, и только.

## MC-11.9: ключ и право им пользоваться

- **Подпись идёт через инструменты** (`release.py`, `sign_manifest.py`). Они читают зерно из файла, названного переменной окружения или аргументом, но никогда из командной строки.
  - Корневые ключи использует только `keys sign`, по одному, так что ни одна машина не держит порога.
  - Ключ меток времени — единственный на сервере публикации, и он подписывает только метки.
- **Устройство не держит ключа, подписывающего обновления.** Ключ устройства `keystore` подписывает для TLS и SSH; `updater` и загрузчик держат только открытые ключи.
- **Чего нет:** аппаратного токена для корневых ключей, ключей выпусков и загрузки. Инструменты читают зёрна из файлов, поэтому машина, у которой есть зерно, может подписать всё, что подписывает этот ключ. Права просить подпись там не отделено от самого ключа.

## Сверка с Конституцией

| Пункт | Что дают этот документ и код | Чего нет |
|---|---|---|
| MC-9.4: нет несанкционированного отката; разрешённый учитывает минимальную версию и отдельные полномочия восстановления; истечение по заданной политике | Порог в загрузочных записях, поднимаемый до минимума канала (351-UPD-0024); опускаемый только распоряжением восстановления, подписанным ролью восстановления (351-UPD-0030); слот ниже версии файла ключей в записях отвергается (351-UPD-0029); метаданные после истечения — как сказано в [updater_RU.md](updater_RU.md) (351-UPD-0025) | Порога, который не опустить с диском в руках (351-UPD-0011, TPM) |
| MC-9.5: ключи, алгоритмы, форматы заменяемы без неявного отказа от проверки | Каждая роль меняется через файл ключей, корень тоже, и при загрузке тоже (351-UPD-0027, 0029); записи прежнего формата и слоты без файла ключей отвергаются, а не читаются непроверенными | Второго алгоритма подписи: только Ed25519 |
| MC-9.6: жизненный цикл, порядок при компрометации, разделение, чего не отменяет смена ключа | Жизненный цикл и порядок выше; пять ролей, у каждой свои ключи и порог; восстановление отдельно от выпусков | Ни один тест не показывает, что шаги людей (где зёрна создают и хранят, когда уничтожают) выполнены |
| MC-11.9: ключевой материал отделён от права просить подпись | На устройстве: только открытые ключи, и ключ `keystore` отдельно от цепочки обновлений. Вне его: инструменты и разделение ролей выше | Аппаратного токена или службы подписи для ключей обновлений |

## Чего ещё нет

- Аппаратного токена или службы подписи, отдельной от машины, которая просит, для корневых ключей, ключей выпусков и загрузки (MC-11.9).
- Инструмента, который создаёт зёрна или проверяет, что один ключ не стоит в двух ролях.
- После компрометации корня на пороге остаётся только новый образ, записанный вручную.
