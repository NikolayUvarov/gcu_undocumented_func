# Secure Boot с нашими ключами

**Версия:** 0.1 (2026-10-08) · **Трек:** `UPD`, задача [351-UPD-0012](../../issues/351-UPD-0012-secure-boot-with-our-own-keys.md) · **Конституция:** MC-9.1, 9.4, 9.6 · English: [secure-boot.md](secure-boot.md)

Загрузчик проверяет ядро и службы по подписанному манифесту ([README.md](README.md)), но сам загрузчик никто не проверяет. Когда Secure Boot включён и записаны ключи проекта, прошивка запускает только загрузчик, подписанный нашим ключом db, и не запускает тот, чей хэш есть в dbx. Именно это делает проверки загрузчика осмысленными против того, кто может писать на диск. Проверено в QEMU, на настоящей машине — ещё нет.

## Ключи

UEFI хранит три вида ключей:
- **PK**, ключ платформы: он разрешает менять KEK;
- **KEK**: он разрешает менять db и dbx;
- **db**: им подписывают загрузчики.

dbx перечисляет отозванное; у нас — хэши Authenticode старых загрузчиков.

`scripts/secure_boot.py keys КАТАЛОГ` делает PK, KEK и db на RSA-2048 с пометкой TEST. Настоящие ключи делаются так же на отдельной машине. Они никогда не попадают в репозиторий, и это не загрузочный ключ и не ключ выпусков (MC-9.6). Закрытые PK и KEK нужны только чтобы записать или сменить ключи, поэтому их держат вне сети. Ключом db подписывают загрузчик каждого выпуска.

## Подпись загрузчика

С `MIND_SECURE_BOOT_KEYS=КАТАЛОГ` (каталог с `db.key` и `db.crt`) `02_build.sh` и `scripts/build_aarch64.sh` подписывают загрузчик через `sbsign` до того, как подписать загрузочный манифест. Манифест тогда перечисляет подписанный загрузчик. Вручную: `scripts/secure_boot.py sign BOOTX64.EFI КАТАЛОГ ВЫХОД`.

## Отзыв загрузчика

Для отзыва выбран **dbx**: хэш Authenticode SHA-256 отзываемого загрузчика (`scripts/secure_boot.py hash OLD.EFI`) записывается в dbx. В QEMU это хранилище переменных, сделанное командой `secure_boot.py vars … --revoke OLD.EFI`. На настоящей машине это аутентифицированное обновление dbx, подписанное нашим KEK, которое применяет программа обновления (351-UPD-0009, 0010). Номер поколения, сверяемый со счётчиком TPM (как SBAT у shim), не используется: dbx не требует TPM, и его соблюдает сама прошивка. Цена в том, что каждый отозванный загрузчик занимает место в dbx.

## Модель доверия

- **Корень доверия** — Secure Boot прошивки с нашими ключами.
- **Чего она не покрывает:**
  - саму прошивку;
  - того, кто может менять настройки прошивки: выключить Secure Boot или записать другие ключи. Поставьте пароль на прошивку;
  - всё, что подписано ключом, который мы записали сами. Машина только с нашими ключами не запускает ничего подписанного Microsoft: ни другую ОС, ни дополнительные ПЗУ устройств, подписанные только Microsoft, пока их ключи или хэши не добавлены сознательно.
- **Профиль** (статья 9) говорит, что проверено: OVMF в QEMU.

## В QEMU

`tests/secure_boot_smoke.py` запускает сборку OVMF с Secure Boot (`OVMF_CODE_4M.secboot.fd`) с хранилищем переменных, сделанным для этого запуска, с тестовыми ключами, и проверяет:
- загрузчик, подписанный нашим ключом db, загружает систему до оболочки;
- прошивка отказывает (`Access Denied`) неподписанному загрузчику, загрузчику с чужой подписью и подписанному, как только его хэш попал в dbx.

CI запускает это в задании «USB image», а `scripts/ci_local.sh` — как «x86: Secure Boot with our keys».

## На настоящем ПК (проверить на машине сопровождающего)

1. **Сделайте ключи** на отдельной машине: `scripts/secure_boot.py keys /secure/mind-keys`. Скопируйте `PK.crt`, `KEK.crt` и `db.crt` на флешку с FAT: настройка прошивки читает сертификаты оттуда (некоторые читают только `.cer`/DER: `openssl x509 -in PK.crt -outform der -out PK.cer`).
2. **Соберите и подпишите:** `MIND_SECURE_BOOT_KEYS=/secure/mind-keys ./02_build.sh`, затем запишите образ как обычно ([docs/write-disk_RU.md](../write-disk_RU.md)).
3. **В настройке прошивки:** поставьте пароль администратора. В меню Secure Boot выберите пользовательский режим и удалите все ключи (прошивка перейдёт в режим настройки). Затем запишите `db.crt` в db, `KEK.crt` в KEK и `PK.crt` в PK, **PK последним**. Включите Secure Boot.
4. **Проверьте:** система загружается с подписанного диска. Диск с неподписанным загрузчиком (сборка без `MIND_SECURE_BOOT_KEYS`) прошивка не запускает.
5. **Чтобы снова загружать другую систему,** сознательно добавьте её ключи или хэши в db или выключите Secure Boot.

Шаги отличаются у разных производителей прошивок. Что делает ПК сопровождающего, записывается вместе с его первым запуском (211-PRT-0004 и [issues-human](../../issues-human/README.md)).

## Чего ещё нет

- запуска на настоящем железе;
- аутентифицированных обновлений dbx, которые применяет программа обновления (351-UPD-0009, 0010);
- Secure Boot на aarch64. Сборка AAVMF с Secure Boot не проверена: загрузчик подписывается так же, но ни один тест aarch64 не записывает ключи;
- пароля или настройки прошивки, которые MIND Core мог бы проверить.
