# Публикация выпусков

**Версия:** 0.6 (2026-11-13): метка времени канала, короткоживущая и продлеваемая без ключа выпусков (351-UPD-0028); 0.5 (2026-11-13): роль `root` файла ключей, его история и цепочка версий на устройстве; смена и отзыв ключей (351-UPD-0027); 0.4 (2026-11-13): файл ключей и корневые ключи, строки подписей, называющие свой ключ (351-UPD-0026); 0.3 (2026-10-10): сторона устройства построена: программа обновления (351-UPD-0007); 0.2: `check` читает поля канала, прежде чем им доверять (351-UPD-0014); 0.1 (2026-10-08) · **Трек:** `UPD`, задача [351-UPD-0005](../../issues-done/351-UPD-0005-release-and-publish.done) · **Конституция:** MC-9.2, 9.4, 9.6, 9.7 · English: [publishing.md](publishing.md)

Как сборка становится выпуском, который устройство может скачать и проверить, как опубликовать его на сервере и кто хранит какой ключ. Сторона устройства — программа обновления ([updater_RU.md](updater_RU.md)): она проверяет канал и готовит его выпуск в слоте с теми же проверками, что и `check` ниже.

## Что такое выпуск

У выпуска есть:
- **версия**: целое число, никогда не используется повторно и никогда не уменьшается;
- для каждой архитектуры загрузочный **манифест** и его подпись, как их сделала сборка ([README.md](README.md));
- каждый файл, который перечисляют эти манифесты. Файл хранится один раз, под своим SHA-256.

**Канал** (`stable`, `test`, …) называет последнюю версию, **минимальную** версию, которую устройству можно запускать, **срок действия** и SHA-256 манифеста каждой архитектуры. Это одна строка JSON в единственной кодировке (ключи по порядку, без пробелов), а затем от одной до восьми строк подписей над этой строкой, `ed25519 <открытый ключ> <подпись>` в hex, от **ключей выпусков**, которые называет файл ключей, не меньше его порога. Всё это лежит в одном файле, поэтому замена файла одним переименованием меняет их вместе.

**Файл ключей** (351-UPD-0026, по образцу корневых метаданных TUF) говорит, какие ключи действуют. Это одна строка JSON в единственной кодировке: его `version`, его `expires` и для каждой роли (`boot`, `recovery`, `release`, `root` и `timestamp`) от одного до четырёх открытых ключей из 64 строчных шестнадцатеричных цифр по возрастанию и `threshold` от 1 до их числа. Затем идут строки подписей того же вида, от **корневых ключей**. Каждый корневой ключ засчитывается один раз, сколько бы строк его ни называли, а строка любого другого ключа пропускается.

Устройство хранит один файл ключей — самую высокую версию, которую оно приняло, — в `system/updater/keys`, который открывает только значок программы обновления (351-UPD-0027, по образцу смены корня в TUF). Оно принимает файл ключей только как **следующую версию** того, что хранит: подписанный порогом роли `root` хранимого файла и порогом роли `root` самого нового файла, которая отличается, когда файл меняет корень. Версию 1 подписывают корневые ключи, встроенные в программу обновления, и её собственная роль `root`. Версия ниже отклоняется: она вернула бы ключ, который отозвала более поздняя; та же версия ещё раз принимается, только если это тот же файл. Устройство, отставшее на несколько версий, читает каждую промежуточную из `keys/<версия>`. Канал, в том числе хранимый в слоте, принимается, только если его подписали ключи выпусков файла ключей, который хранит устройство: ключ, которого этот файл больше не называет, не засчитывается, поэтому слот, чей канал подписал только такой ключ, — не запасной, и его версия не известна. Канал прежнего вида, чья единственная строка `ed25519 <подпись>` не называет ключа, отклоняется (MC-12.4). Сейчас программа обновления пользуется ролью `release`; роли `boot`, `recovery` и `timestamp` названы для [351-UPD-0029](../../issues/351-UPD-0029-the-boot-key-under-the-root.md), [351-UPD-0030](../../issues/351-UPD-0030-a-separate-recovery-authority.md) и [351-UPD-0028](../../issues/351-UPD-0028-a-short-lived-timestamp-key.md).

```
{"expires":"2027-11-13T00:00:00Z","roles":{"boot":{"keys":["662f…"],"threshold":1},"recovery":{…},"release":{"keys":["98d6…"],"threshold":1},"root":{"keys":["1a4c…","5e07…","c3b9…"],"threshold":2},"timestamp":{…}},"version":1}
ed25519 <корневой ключ 1> <его подпись первой строки>
ed25519 <корневой ключ 2> <его подпись первой строки>
```

**Метка времени** канала (351-UPD-0028, по образцу метаданных timestamp в TUF) говорит, что канал действует. Это одна строка JSON в единственной кодировке: `channel`, SHA-256 файла канала в опубликованном виде (`digest`, вместе с подписями), короткий `expires` (по умолчанию 24 часа) и собственная `version`, которую повышает каждое продление. Затем идут строки подписей **ключей меток времени**, которые называет роль `timestamp` файла ключей. Устройство читает метку раньше канала и отклоняет её, если ключи меток не подписали её до порога, если её версия ниже уже принятой или если её срок истёк; затем оно берёт только тот файл канала, который она называет. Канал действует не дольше своей метки: сервер или любой, у кого есть старый файл, может задержать устройство на последнем подписанном канале на сутки, а не на недели срока канала (приложение B.5). Источник без метки отклоняется (`missing`).

```
{"channel":"stable","digest":"9c1f…","expires":"2026-11-14T06:00:00Z","version":12}
ed25519 <ключ меток> <его подпись первой строки>
```

Раскладка на сервере:

```
blobs/<sha256>                              каждый файл каждого выпуска, по содержимому
releases/<версия>/<arch>/MANIFEST           загрузочный манифест этой архитектуры
releases/<версия>/<arch>/MANIFEST.SIG       его подпись (загрузочный ключ)
channels/<канал>                            подписанный файл канала (ключи выпусков)
keys/current                                файл ключей (корневые ключи)
keys/<версия>                               каждая его версия начиная с 1: подписана корнем предыдущей и своим
timestamps/<канал>                          метка времени канала (ключи меток)
```

## Как сделать и опубликовать выпуск

```bash
./02_build.sh && ARCH=aarch64 ./02_build.sh                # собирает и подписывает usb_root/ и aarch64_root/
python3 scripts/release.py stage 7 /tmp/release-7          # проверяет каждый том, затем копирует его как версию 7
python3 scripts/release.py publish /tmp/release-7 updates@example.org:/srv/mind --channel stable --minimum 5
python3 scripts/release.py check /srv/mind --channel stable   # на сервере или на копии
python3 scripts/release.py bundle /srv/mind /tmp/mind-7.zip --arch x86_64   # один файл для шлюза Effector
python3 scripts/release.py timestamp updates@example.org:/srv/mind --channel stable   # на сервере, не реже раза в сутки
```

Метку продлевают одним ключом меток (`$MIND_TIMESTAMP_KEY`), который хранится на сервере публикации; ключ выпусков там не нужен. Продлевайте её заранее, по таймеру на этом сервере: устройство, не получившее действующей метки, держит то, что у него есть, как после срока канала ([updater_RU.md](updater_RU.md)).

Файл ключей делают один раз и снова при смене ключа. Его подписывают по одному корневому ключу на машинах, где те хранятся:

```bash
python3 scripts/release.py keys root /media/root1.seed /media/root2.seed /media/root3.seed --threshold 2 > root.pub   # файл для $MIND_ROOT_KEYS
python3 scripts/release.py keys make keys-1 --version 1 --days 365 --role boot=<ключ>:1 --role recovery=<ключ>:1 --role release=<ключ>:1 \
    --role root=<корневой ключ 1>,<корневой ключ 2>,<корневой ключ 3>:2 --role timestamp=<ключ>:1
python3 scripts/release.py keys sign keys-1 /media/root1.seed                 # на машине первого корневого ключа
python3 scripts/release.py keys sign keys-1 /media/root3.seed                 # на машине другого
python3 scripts/release.py keys check keys-1 --root root.pub
python3 scripts/release.py keys publish keys-1 updates@example.org:/srv/mind --root root.pub
```

- `keys make` пишет только тело. `keys sign` добавляет одну строку и отказывает ключу, который уже подписал. `keys check` говорит, сколько корневых ключей подписали файл — из данного набора и из его собственной роли `root`, — и его срок.
- `keys publish` проверяет каждую версию на сервере начиная с 1, каждую по корню предыдущей; затем файл — по корню последней и по своему — и пишет `keys/<версия>` и `keys/current`. Публикуется только следующая версия; тот же файл ещё раз ничего не меняет.

### Смена и отзыв ключа (351-UPD-0027)

Ключ заменяют или отзывают, публикуя следующую версию файла ключей:

```bash
python3 scripts/release.py keys rotate keys-1 release keys-2 --key <новый ключ выпусков> --threshold 1   # ключ выпусков заменён
python3 scripts/release.py keys revoke keys-1 <ключ> keys-2                    # или: ключ убран из всех ролей
python3 scripts/release.py keys sign keys-2 /media/root1.seed                  # порог текущего корня…
python3 scripts/release.py keys sign keys-2 /media/root3.seed
python3 scripts/release.py keys publish keys-2 updates@example.org:/srv/mind --root root.pub
python3 scripts/release.py publish /tmp/release-8 updates@example.org:/srv/mind   # затем канал, подписанный новым ключом
```

- `rotate` и `revoke` пишут тело следующей версии из текущего файла с новым сроком (`--days`). `revoke` отказывает, если в роли останется меньше ключей, чем её порог: смените тогда эту роль.
- **Смена корня** (`keys rotate ФАЙЛ root ВЫХОД --key K1,K2,K3 --threshold 2`): новый файл подписывают порог текущего корня **и** порог нового. После этого каждое устройство доверяет только новому корню; старые корневые ключи больше не подписывают ничего, что устройство примет.
- Когда устройство приняло новую версию, канал, который подписал только старый ключ выпусков, отклоняется, а слот, чей хранимый канал подписал только он, — не запасной. Поэтому сразу за файлом ключей публикуйте канал, подписанный новым ключом. Сервер, снова отдающий старый файл ключей, получает отказ от каждого устройства, принявшего новый.
- `$MIND_ROOT_KEYS` остаётся корневым набором, которым подписана версия 1 и с которым собрана программа обновления: `keys publish` и `check` проходят историю от него.

- `stage` отказывает тому, чей манифест не проходит проверку. Выпуски делаются только из подписанных сборок.
- `publish` отказывает версии не выше версии канала, версии, чьи манифесты уже есть на сервере, и ключам выпусков, которых не называет файл ключей сервера или которых меньше его порога для выпусков. Сервер без файла ключей получает тестовый, если канал подписан одним тестовым ключом выпусков; с любым другим ключом публикация отклоняется. Он загружает в таком порядке:
  1. файлы, никогда не перезаписывая уже загруженный;
  2. манифесты выпуска;
  3. канал, одним переименованием;
  4. метку времени канала, её версия на одну выше серверной (351-UPD-0028).

  Если загрузка оборвётся в любой момент, прежний канал по-прежнему называет только файлы, которые на месте. Пока метки нет, устройство отклоняет новый канал (`digest`) и держит прежний.
- Назначение — каталог на этой машине или `хост:каталог`, куда идёт системный OpenSSH (`ssh`, `rsync -e ssh`). Вход по SSH принадлежит тому, кто загружает, и это никогда не ключ выпусков.
- `check` проверяет:
  - историю файла ключей начиная с `keys/1`, каждую версию — по корню предыдущей и своему (версию 1 — по набору из `$MIND_ROOT_KEYS`, без него — по тестовому), и `keys/current`, последнюю из них: их вид и срок последней;
  - подписи канала: не меньше порога для выпусков ключей, которые называет файл ключей; затем его поля так, как их читает устройство (UTF-8 JSON из `channel`, `version`, `minimum`, `expires` и `manifests`, каждое своего типа и диапазона: 1 ≤ minimum ≤ version < 2^64, `expires` — настоящее время вида `YYYY-MM-DDTHH:MM:SSZ`, от 1 до 4 архитектур с 64 строчными шестнадцатеричными цифрами каждая), его единственную кодировку и срок действия. Тело, подписанное ключом выпусков, но не являющееся каналом, получает причину, а не исключение (351-UPD-0014);
  - метку времени канала: порог ключей меток, которые называет файл ключей, файл канала, который она называет, и её срок (351-UPD-0028);
  - каждый манифест, который он называет: его хэш и загрузочную подпись;
  - каждый файл, который перечисляют манифесты: размер и хэш.
- `bundle` сначала выполняет `check`, затем пишет один ZIP с несжатыми записями и постоянными датами (751-UPD-0032):
  - историю файла ключей начиная с `keys/1` (351-UPD-0027) и файл ключей;
  - файл канала и его метку времени (351-UPD-0028): архив ставят в пределах срока метки, иначе её продлевают и делают архив снова;
  - манифест и подпись каждой запрошенной архитектуры (по умолчанию — всех, что называет канал);
  - файлы, которые эти манифесты перечисляют.

  Шлюз Effector передаёт его `updater` (`update.wit` 1.3 `install-…`), а тот проверяет его как любой источник ([updater_RU.md](updater_RU.md)). Один и тот же выпуск даёт один и тот же файл.

## Ключи и кто их хранит (MC-9.6)

| Ключ | Подписывает | Хранит | В этом репозитории |
|---|---|---|---|
| Загрузочный ключ | загрузочные манифесты (`MANIFEST.SIG`) | тот, кто собирает выпуск; открытая половина встроена в загрузчик | только **тестовый**, выведенный из открытого текста (`scripts/sign_manifest.py`) |
| Корневые ключи | файлы ключей (`keys/<версия>`), не меньше корневого порога: предыдущей версии и своей роли `root` | каждый отдельно от других, вне сети; открытые половины и порог первого набора встроены в программу обновления, действующие называет роль `root` файла ключей | только **тестовый** набор: три ключа из фиксированного текста, подписывают два (`scripts/release.py`) |
| Ключи выпусков | файлы каналов, не меньше порога для выпусков | тот, кто публикует; их называет файл ключей | только **тестовый** (`scripts/release.py`) |
| Ключи меток времени | файлы меток, не меньше порога меток (351-UPD-0028) | сервер публикации, который продлевает метку; их называет файл ключей | только **тестовый** (`scripts/release.py`) |
| Вход по SSH | ничего: он даёт загружающему писать на сервер | собственный SSH-ключ загружающего | нет |

- Настоящий ключ — файл из 64 шестнадцатеричных цифр (32-байтовое зерно) вне репозитория. Его называют `$MIND_BOOT_SIGNING_KEY`, `$MIND_RELEASE_KEY` и `$MIND_TIMESTAMP_KEY` (несколько ключей выпусков или меток — через разделитель путей); корневой ключ передаётся только `keys sign`. Загрузчик собирается с открытой половиной загрузочного ключа (`$MIND_BOOT_PUBLIC_KEY`). Программа обновления собирается с ней и с открытым файлом корневого набора `$MIND_ROOT_KEYS` (`threshold T`, затем по ключу в строке, как его печатает `keys root`). Ключ выпусков в неё не встроен: ключи выпусков называет файл ключей (половину тестового ключа выпусков печатает `release.py --public`).
- Тестовые ключи открыты. Выпуск, подписанный ими, проверяется на случайности, а не против нападающего. Программы так и пишут: `THE TEST KEY` / `THE TEST RELEASE KEY` / `THE TEST ROOT KEYS`.
- Смена и отзыв ключей описаны выше (351-UPD-0027). Загрузочный ключ при загрузке пока не подчинён файлу ключей ([351-UPD-0029](../../issues/351-UPD-0029-the-boot-key-under-the-root.md)), а порядок действий при компрометации — кто что меняет и когда — ещё не определён ([351-UPD-0031](../../issues/351-UPD-0031-key-lifecycle-and-compromise-protocol.md)).
- Устройство, чей образ записан, когда файл ключей был выше версии 1, при первом запуске не берёт файла ключей из слотов, и его первая проверка читает версии с сервера начиная с 1.

## Как настроить сервер

Любой статический веб-сервер поверх каталога отдаёт канал по HTTPS. Собственный сервер проекта, `httpd` ([server_RU.md](server_RU.md)), — этап 1 основной задачи [110](../../issues/110-our-own-web-server.md): программа для Linux, TLS 1.3 с закреплённым ключом; служба MIND Core — этап 2. Учётной записи SSH, от имени которой публикуют, нужна только запись в этот каталог. Для тестов `scripts/serve_release.py КАТАЛОГ --cert … --key …` отдаёт каталог по TLS 1.3 с сертификатом, который даёт тест.

## Чего ещё нет

- клиента SSH программы обновления (351-NET-0004);
- политики для минимальной версии канала на устройстве сверх сообщения о ней;
- тестового SSH-сервера в CI (сервера OpenSSH на исполнителях нет; путь `publish` через SSH не проверен тестом).
