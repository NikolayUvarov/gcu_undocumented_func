# Публикация выпусков

**Версия:** 0.3 (2026-10-10): сторона устройства построена: программа обновления (351-UPD-0007); 0.2: `check` читает поля канала, прежде чем им доверять (351-UPD-0014); 0.1 (2026-10-08) · **Трек:** `UPD`, задача [351-UPD-0005](../../issues-done/351-UPD-0005-release-and-publish.done) · **Конституция:** MC-9.2, 9.4, 9.6, 9.7 · English: [publishing.md](publishing.md)

Как сборка становится выпуском, который устройство может скачать и проверить, как опубликовать его на сервере и кто хранит какой ключ. Сторона устройства — программа обновления ([updater_RU.md](updater_RU.md)): она проверяет канал и готовит его выпуск в слоте с теми же проверками, что и `check` ниже.

## Что такое выпуск

У выпуска есть:
- **версия**: целое число, никогда не используется повторно и никогда не уменьшается;
- для каждой архитектуры загрузочный **манифест** и его подпись, как их сделала сборка ([README.md](README.md));
- каждый файл, который перечисляют эти манифесты. Файл хранится один раз, под своим SHA-256.

**Канал** (`stable`, `test`, …) называет последнюю версию, **минимальную** версию, которую устройству можно запускать, **срок действия** и SHA-256 манифеста каждой архитектуры. Это одна строка JSON в единственной кодировке (ключи по порядку, без пробелов), а затем `ed25519 <подпись в hex>` над этой строкой, подписанная **ключом выпусков**. Обе строки лежат в одном файле, поэтому замена файла одним переименованием меняет их вместе.

Раскладка на сервере:

```
blobs/<sha256>                              каждый файл каждого выпуска, по содержимому
releases/<версия>/<arch>/MANIFEST           загрузочный манифест этой архитектуры
releases/<версия>/<arch>/MANIFEST.SIG       его подпись (загрузочный ключ)
channels/<канал>                            подписанный файл канала (ключ выпусков)
```

## Как сделать и опубликовать выпуск

```bash
./02_build.sh && ARCH=aarch64 ./02_build.sh                # собирает и подписывает usb_root/ и aarch64_root/
python3 scripts/release.py stage 7 /tmp/release-7          # проверяет каждый том, затем копирует его как версию 7
python3 scripts/release.py publish /tmp/release-7 updates@example.org:/srv/mind --channel stable --minimum 5
python3 scripts/release.py check /srv/mind --channel stable   # на сервере или на копии
```

- `stage` отказывает тому, чей манифест не проходит проверку. Выпуски делаются только из подписанных сборок.
- `publish` отказывает версии не выше версии канала и версии, чьи манифесты уже есть на сервере. Он загружает в таком порядке:
  1. файлы, никогда не перезаписывая уже загруженный;
  2. манифесты выпуска;
  3. канал, одним переименованием.

  Если загрузка оборвётся в любой момент, прежний канал по-прежнему называет только файлы, которые на месте.
- Назначение — каталог на этой машине или `хост:каталог`, куда идёт системный OpenSSH (`ssh`, `rsync -e ssh`). Вход по SSH принадлежит тому, кто загружает, и это никогда не ключ выпусков.
- `check` проверяет:
  - подпись канала; затем его поля так, как их читает устройство (UTF-8 JSON из `channel`, `version`, `minimum`, `expires` и `manifests`, каждое своего типа и диапазона: 1 ≤ minimum ≤ version < 2^64, `expires` — настоящее время вида `YYYY-MM-DDTHH:MM:SSZ`, от 1 до 4 архитектур с 64 строчными шестнадцатеричными цифрами каждая), его единственную кодировку и срок действия. Тело, подписанное ключом выпусков, но не являющееся каналом, получает причину, а не исключение (351-UPD-0014);
  - каждый манифест, который он называет: его хэш и загрузочную подпись;
  - каждый файл, который перечисляют манифесты: размер и хэш.

## Ключи и кто их хранит (MC-9.6)

| Ключ | Подписывает | Хранит | В этом репозитории |
|---|---|---|---|
| Загрузочный ключ | загрузочные манифесты (`MANIFEST.SIG`) | тот, кто собирает выпуск; открытая половина встроена в загрузчик | только **тестовый**, выведенный из открытого текста (`scripts/sign_manifest.py`) |
| Ключ выпусков | файлы каналов | тот, кто публикует | только **тестовый** (`scripts/release.py`) |
| Вход по SSH | ничего: он даёт загружающему писать на сервер | собственный SSH-ключ загружающего | нет |

- Настоящий ключ — файл из 64 шестнадцатеричных цифр (32-байтовое зерно) вне репозитория. Его называют `$MIND_BOOT_SIGNING_KEY` и `$MIND_RELEASE_KEY`. Загрузчик собирается с открытой половиной загрузочного ключа (`$MIND_BOOT_PUBLIC_KEY`), а программа обновления — с обеими открытыми половинами (`$MIND_BOOT_PUBLIC_KEY`, `$MIND_RELEASE_PUBLIC_KEY`; половину ключа выпусков печатает `release.py --public`).
- Тестовые ключи открыты. Выпуск, подписанный ими, проверяется на случайности, а не против нападающего. Программы так и пишут: `THE TEST KEY` / `THE TEST RELEASE KEY`.
- Смена ключей, отзыв и порядок действий при компрометации ещё не определены ([351-UPD-0009](../../issues/351-UPD-0009-rollback-policy-and-key-roles.md)).

## Как настроить сервер

Любой статический веб-сервер поверх каталога отдаёт канал по HTTPS. Учётной записи SSH, от имени которой публикуют, нужна только запись в этот каталог. Для тестов `scripts/serve_release.py КАТАЛОГ --cert … --key …` отдаёт каталог по TLS 1.3 с сертификатом, который даёт тест.
