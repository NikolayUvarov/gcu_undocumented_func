# Сервер выпусков, `httpd`

**Версия:** 0.1 (2026-11-11) · **Трек:** `NET` ([TRACKS.md](../../TRACKS.md)), основная задача [110](../../issues/110-our-own-web-server.md) · **English:** [server.md](server.md)

`tools/httpd` — собственный веб-сервер проекта для выпусков: программа для Linux, которая отдаёт раскладку `scripts/release.py` только на чтение. Это этап 1 задачи [110](../../issues/110-our-own-web-server.md). Проверки `update` в QEMU пока идут против `scripts/serve_release.py`, и ни одно устройство ещё не обновлялось с `httpd`.

## Чему он доверен, а чему нет

- **Не подлинности обновления.** Выпуск подписан ключом загрузки и ключом выпуска, и устройство проверяет оба (MC-9.6). Взломанный сервер не может его подделать.
- **Он может задержать или не отдать выпуск.** Это ограничивает срок годности канала ([351-UPD-0025](../../issues-done/351-UPD-0025-expiry-and-the-offline-policy.done)).
- **Он хранит ключ TLS, который устройства закрепляют.** Тот, кто завладел ключом, может выдать себя за сервер, но подделать выпуск всё равно не может.

## Сборка и запуск

```
cd tools/httpd && cargo build --release
target/release/httpd /srv/mind --cert chain.pem --key key.pem --listen 0.0.0.0:443 --log /var/log/mind-httpd
```

- **Корень** — каталог, в который пишет `release.py publish`: `blobs/`, `releases/`, `channels/`. Ничего другого под ним не отдаётся: каждое имя сверяется со своим образцом, а ссылки, имена с точки, запросы с параметрами и закодированные байты отвергаются.
- **Публикация не меняется.** `publish` пишет по SSH и переименовывает канал последним. Каждый запрос открывает свой файл один раз, поэтому читатель получает старый канал или новый целиком.
- **Без `--cert` и `--key`** сервер говорит на открытом HTTP — для закрытой сети или теста.

## TLS и закрепление ключа

- **Только TLS 1.3,** с AES-GCM и ChaCha20-Poly1305, X25519 и P-256: rustls 0.23 поверх крейтов RustCrypto, как в сервисе `tls` ([THIRD_PARTY.md](../../THIRD_PARTY.md)).
- **Ключ:** ECDSA P-256 или Ed25519, в PEM PKCS#8 или SEC1. Ключ RSA загружается только с `--allow-rsa`: подпись крейта `rsa` не постоянна по времени (RUSTSEC-2023-0071), поэтому он только для тестовых сертификатов.
- **Закрепление.** При запуске сервер печатает `HTTPD: TLS 1.3, THE KEY'S SPKI SHA-256 <hex>`. Это значение принимает `pin` в `update.txt` ([updater_RU.md](updater_RU.md)).
- **Продление сохраняет ключ.** Сервер перечитывает сертификат и ключ, когда их файлы меняются; проверка раз в 10 с. Уже открытые соединения остаются со старым сертификатом.
  - Новый сертификат на тот же ключ: `HTTPD: THE CERTIFICATE RELOADED, THE SAME KEY`.
  - Новый ключ: сервер говорит об этом, потому что устройство, закрепившее только старый ключ, его отвергнет. Новый ключ публикуется вторым закреплением до того, как его начинают использовать ([351-UPD-0031](../../issues/351-UPD-0031-key-lifecycle-and-compromise-protocol.md)).
  - Пара, которая не загружается, или ключ не от этого сертификата: остаётся прежняя пара, и сервер говорит почему.

## Пределы

Каждый отказ называет предел, в который упёрся, в ответе и в журнале.

| Флаг | По умолчанию | Отказ |
|---|---|---|
| `--connections` | 64 одновременно | 503 (по TLS соединение закрывается) |
| `--per-client` | 8 одновременно с одного адреса | 503 (так же) |
| `--per-minute` | 600 запросов с адреса | 429, с `Retry-After` |
| (постоянно) | заголовок до 8 КиБ, 64 строки | 431 |
| (постоянно) | 10 с на заголовок, 10 с между байтами | 408 |

## Журнал

- Одна строка на запрос: время, адрес клиента, метод, путь, статус, отправленные байты, длительность и причина отказа.
- Один файл в день, `httpd-YYYY-MM-DD.log`, в `--log`; файлы старше `--log-days` (30) удаляются. Без `--log` строки идут в стандартный поток ошибок.
- В нём никогда нет строки запроса или значения заголовка; байты вне алфавита имён показаны как `?`.

## Чего ещё нет

- проверок `update` и `linkupdate` в QEMU против `httpd` и устройства, обновлённого с сервера сопровождающего (110, этап 1);
- цели фаззинга для разбора запроса;
- того же сервера как службы MIND Core (этап 2).
