`updater` — загрузочный сервис, который превращает опубликованный выпуск ([publishing_RU.md](publishing_RU.md)) в подготовленный и проверенный слот ([slots_RU.md](slots_RU.md)), и ничего больше. Он держит:
- свою конечную точку;
- часы;
- клиента `vfs_server` со значком зоны обновления: слот, из которого система не загрузилась, и две загрузочные записи; а также своего личного каталога `system/updater`, который не открывает никакой другой значок (351-UPD-0027);
- сервис разбора;
- клиента `init` со значком для `reboot`;
- журнал;
- сетевой грант, который политика сети даёт `updater`;
- клиента TLS;
- клиента блочного хранилища со значком `OWNER_UPDATER` и правами get, put и publish, когда хранилище работает (351-KRN-0218).

Ничего другого он записать не может, а манифест, который он читает, ничего не разрешает (MC-3.11).

## Что он проверяет

- **Файл ключей** (`keys/current`, 351-UPD-0026, [publishing_RU.md](publishing_RU.md)), первым. Его читает сервис разбора, и `updater` берёт его так же, как поля канала ниже. Он хранит один файл ключей — самую высокую принятую версию (351-UPD-0027) — и принимает другой только как **следующую версию** (`release::step`): подписанный не меньше порога роли `root` хранимого файла (для версии 1 — встроенных корневых ключей) и порога роли `root` самого нового файла; каждый корневой ключ засчитывается один раз, строка любого другого ключа пропускается. Источник, ушедший на несколько версий вперёд, отдаёт каждую промежуточную как `keys/<версия>`, и они принимаются по очереди. Затем проверяется срок последней по часам. До того, как прочитан какой-либо канал:
  - файл, который корень предыдущей версии не подписал до порога, отклоняется: `[UPDATER] KEY FILE VERSION 2 REFUSED (keys/current): FEWER THAN 2 OF VERSION 1'S ROOT KEYS SIGNED IT`;
  - версия ниже отклоняется (`older`): она вернула бы ключ, отозванный более поздней: `[UPDATER] KEY FILE VERSION 1 REFUSED (keys/current): BELOW VERSION 3, TAKEN BEFORE: IT WOULD BRING REVOKED KEYS BACK`;
  - та же версия принимается, только если это тот же файл.

  Каждая принятая версия хранится в `system/updater/keys`: сначала пишется целиком рядом (`keys.new`), затем ставится на место: `[UPDATER] KEY FILE VERSION 3 TAKEN (keys/current), THE ROOT ROTATED, KEPT IN system/updater/keys`. При запуске `updater` читает её обратно — ту из двух, что выше и подписана своим корнем (`[UPDATER] KEY FILE VERSION 3 FROM system/updater/keys, TAKEN BEFORE`). Если хранимого нет, он берёт `KEYS` слота, когда это следующая версия: в только что записанном образе там версия 1.
- **Метку времени** (`timestamps/<канал>`, 351-UPD-0028), следом. Её читает сервис разбора, как канал ниже. Она отклоняется — до того, как прочитан канал, и без единой записи, — если:
  - её подписали меньше порога ключей меток, которые называет файл ключей: `[UPDATER] TIMESTAMP VERSION 9 REFUSED: FEWER THAN 1 OF THE TIMESTAMP KEYS OF KEY FILE VERSION 1 SIGNED IT` (`signature`);
  - она другого канала (`malformed`);
  - её версия ниже самой высокой, принятой раньше; та хранится в `system/updater/timestamp` между перезапусками (`older`);
  - её срок истёк или часы не читаются (`expired`).

  Затем файл канала должен быть тем, который она называет по SHA-256 (`[UPDATER] TIMESTAMP VERSION 9 NAMES ANOTHER FILE THAN channels/stable`, `digest`). Сроком канала считается меньший из его собственного и срока метки: его показывают `metadata` и журнал, и `apply` ждёт, пока он истёк. Откату и выпуску, записываемому заново из блочного хранилища, метка не нужна.
- **Канал.** Его поля читает сервис разбора, и `updater` берёт их, только если они кодируются обратно ровно в полученные байты (MC-11.11). Затем он проверяет:
  - строки подписей первой строки: не меньше порога роли `release` из **ключей выпусков**, которые называет файл ключей;
  - имя канала;
  - срок действия по часам. Если часы не читаются, канал считается просроченным: `updater` не берёт метаданные, свежесть которых не может показать (MC-9.4). Что делает устройство после срока, сказано [ниже](#метаданные-после-срока-действия).
- **Версию.** Канал, версия которого не выше работающей, отклоняется (`older`). Работающую версию показывает канал, сохранённый в работающем слоте: канал должен проверяться ключами выпусков файла ключей, который хранит `updater`, и называть для этой архитектуры тот манифест, который загрузчик проверил и загрузил (его дайджест есть в `BootInfo`). У слота без такого канала, например сделанного `boot_slots.py layout`, версия 0, «неизвестна». Так же и у слота, чей канал подписал только ключ, которого хранимый файл больше не называет (351-UPD-0027), и такой слот — не запасной: `[UPDATER] SLOT A: ITS CHANNEL IS SIGNED BY FEWER THAN 1 OF THE RELEASE KEYS OF KEY FILE VERSION 3: NOT A FALLBACK`.
- **Манифест** этой архитектуры: его SHA-256 должен совпадать с названным в канале, а подпись должна быть сделана ключом роли `boot` файла ключей, которому доверяет программа обновления (351-UPD-0029), роли с порогом 1: манифест несёт одну подпись. Иначе `[UPDATER] FETCH: VERSION 7: ITS MANIFEST IS SIGNED BY NO BOOT KEY OF KEY FILE VERSION 2`.
- **Каждый файл слота** из манифеста, по размеру и SHA-256 после записи на диск: `kernel.elf`, сервисы из `BOOT_FILES`, загрузчик для своего процессора (`EFI/BOOT/BOOTX64.EFI`, кладётся в слот как `BOOTX64.EFI`, 351-UPD-0010, [slots_RU.md](slots_RU.md)) и приложения, то есть все остальные `*.elf` в корне манифеста (351-UPD-0023). Лицензии и данные остаются в корне тома, общие для обоих слотов ([slots_RU.md](slots_RU.md)), и не загружаются.

При сборке встраиваются только открытые ключи корневого набора: `$MIND_ROOT_KEYS` (`threshold T`, затем по открытому ключу в строке, как его печатает `release.py keys root`) или открытый тестовый набор (`updater/keys/root-test.pub` — три ключа, подписывают два); загрузчик собирается с тем же набором (351-UPD-0029). Других ключей не встраивается: ключи загрузки, выпусков, меток времени и восстановления называет файл ключей. С тестовым набором `updater` сообщает об этом при запуске (`[UPDATER] KEYS: THE TEST ROOT KEYS`).

**Файлы ключей слота** (351-UPD-0029). Вместе с манифестом и его подписью программа обновления кладёт в слот файл ключей, которому доверяет, `KEYS`, а перед ним — принятые ею файлы ключей, менявшие корень, как `KEYS.1`, `KEYS.2`, …: по ним загрузчик идёт от встроенного корня. Она хранит их в `system/updater/roots/<версия>`, принимая (`[UPDATER] KEY FILE VERSION 3 TAKEN (keys/current), THE ROOT ROTATED, KEPT IN system/updater/keys AND system/updater/roots`). Перед применением и перед распоряжением восстановления она проверяет файлы ключей другого слота так, как их проверит загрузчик (`bootloader/src/keychain.rs`, каждый файл читает служба разбора): под встроенным корнем, с версией не ниже той, что называют записи, и с манифестом, подписанным загрузочным ключом, который они называют. Слот ниже этой версии, чей манифест подписан загрузочным ключом доверенного файла, сначала получает доверенные файлы ключей (`[UPDATER] SLOT A: KEY FILE VERSION 2 WRITTEN THERE, A BOOT KEY OF WHICH SIGNED ITS MANIFEST`).

**Версия файла ключей в записях** (351-UPD-0029, [slots_RU.md](slots_RU.md)). Подтверждение слота переносит в записи версию его файла ключей, не ниже той, что в них уже есть (`[UPDATER] KEY FILE VERSION 2 IN THE RECORDS: A SLOT WITH A LOWER ONE IS NOT BOOTED (MC-9.6)`). С этих пор загрузчик отвергает слот, чей файл ключей ниже неё. Когда версия растёт, другой слот сначала получает доверенные файлы ключей, если его манифест подписан загрузочным ключом, который они называют, и остаётся запасным; иначе программа обновления говорит, что он не запасной: `[UPDATER] SLOT A: SIGNED BY NO BOOT KEY OF KEY FILE VERSION 2: NOT A FALLBACK FROM NOW ON`.

## Что он делает

| Запрос (`idl/update.wit`) | Что происходит |
|---|---|
| `check` | Канал, проверенный как выше. Возвращает предложение и работающую версию. |
| `fetch` | `check`, затем новый выпуск в слот, из которого система не загрузилась. Сначала он удаляет из слота `CHANNEL`, `KEYS`, `MANIFEST`, `MANIFEST.SIG` и все файлы, которых нет в новом манифесте (загрузчик отвергает слот с загрузочным файлом, которого нет в манифесте). Затем загружает каждый загрузочный файл, загрузчик и каждое приложение. Приложение, которое уже есть на томе в том виде, как его перечисляет манифест (в работающем слоте или в корне), вместо этого копируется оттуда. Неполный файл продолжается с места, где он кончается, оборванное соединение продолжается через `Range`, а файл не такой, как в манифесте, загружается ещё раз целиком и потом отклоняется. Последними идут `MANIFEST`, `MANIFEST.SIG`, файл ключей как `KEYS` и `CHANNEL`: канал появляется в слоте только когда там есть всё остальное. |
| `apply` | Проверяет другой слот так же, как его проверит загрузчик: подпись манифеста, все перечисленные загрузочные файлы, отсутствие неперечисленных и его загрузчик, если он там есть, в том виде, как его перечисляет манифест (в слоте, подготовленном до 351-UPD-0010, его нет). Слот, в котором есть приложения, должен содержать все приложения из манифеста и ни одного другого. В слоте, подготовленном до 351-UPD-0023, приложений нет, и работают приложения из корня. Канал в нём должен показывать версию выше работающей, и его срок не должен истечь (`expired`). Если слот не совпадает со своим манифестом, а блочное хранилище держит подготовленный там выпуск выше работающей версии, этот выпуск сначала записывается туда заново из хранилища (1.5, [ниже](#выпуски-в-блочном-хранилище-351-upd-0033)). Затем пишет запись, которая загружает этот слот на пробу с 1–9 попытками и откатом на работающий слот, и просит `init` перезапустить машину. |
| `rollback` | Та же проверка другого слота. Если слот не совпадает со своим манифестом, а блочное хранилище держит последний рабочий выпуск, этот выпуск сначала записывается туда заново из хранилища (1.4, [ниже](#выпуски-в-блочном-хранилище-351-upd-0033)). Канал в нём должен показывать версию не ниже наибольшего минимума, который видел `updater` (канал работающего слота и последняя проверка). Затем пишет запись, которая загружает этот слот на пробу с откатом на работающий, и просит `init` перезапустить машину. |
| (порог) | Не запрос: когда работающий слот подтверждён, программа обновления поднимает порог версии до наибольшего минимума из проверенного канала, если собственный манифест работающего слота называет эту версию или выше; никогда вниз. Она снова пишет более новую запись, на единицу дальше, с этим порогом (`plan::raise`), а каждая другая её запись переносит порог дальше. Записи формата 1 она называет при старте и не читает (`RECORD MIND/BOOT0 OF FORMAT 1, NOT READ`). Загрузчик не загружает слот ниже порога ([slots_RU.md](slots_RU.md#порог-версии-351-upd-0024)). Откат на выпуск не ниже минимума остаётся разрешён. |
| `status` | Работающий слот, загружен ли он на пробу, его версия, слот новой записи и подтверждена ли она, версия, подготовленная в другом слоте, и последняя ошибка. |
| `metadata` (1.1) | Канал, который держит `updater`, проверенный ключами выпусков из его файла ключей: последний прочитанный из источника или из пакета, а если такого нет — сохранённый в работающем слоте. Его имя, версия, минимум и срок действия, истёк ли срок и прочитан ли канал после запуска `updater`. |
| `kept` (1.5) | Выпуски, которые блочное хранилище держит для `updater`, от новых к старым, не больше 8; без хранилища — ни одного. Для каждого: версия, закрепление, которое его держит, корень дерева и байты файлов, которые его манифест перечисляет для слота, каждый по одному разу (351-UPD-0035). Спросить может любой клиент `updater`. |
| `install-begin` (1.3) | Только от клиента шлюза Effector (`BADGE_UPDATE_GATEWAY`) и только пока у `init` действует `remote-update`; любой другой клиент получает `denied` (751-UPD-0032). Начинает пакет названного размера и SHA-256 в `MIND/<другой слот>/INSTALL/BUNDLE.ZIP`, который не читают ни загрузчик, ни `fetch`. Идентификатор команды шлюза попадает в журнал (MC-10.3). Ранее начатый пакет удаляется, как и оставленный перезапуском. |
| `install-write` (1.3) | Байты пакета со смещения не дальше уже записанного: то, что лежало с этого места и дальше, удаляется, так что оборванная передача продолжается. |
| `install-commit` (1.3) | Снова спрашивает `remote-update`, проверяет размер и SHA-256 пакета (`digest`), читает его как ZIP с несжатыми записями (иначе `malformed`: сжатие, шифрование, ZIP64, имя, выходящее из дерева или повторённое, диапазон вне файла), затем ставит содержащийся в нём выпуск так же, как `fetch` ставит выпуск источника, с теми же проверками, и удаляет пакет. В пакете то, что пишет `release.py bundle`: канал, названный в `update.txt`, его манифесты с подписями и перечисленные в них файлы. Затем шлюз вызывает `apply`, который снова спрашивает `remote-update`. |

Пока работающий слот на пробе и ещё не подтверждён на диске, другой слот не пишется: он тогда служит откатом. Запрос выполняется до конца, прежде чем читается следующий.

**Подтверждение пробы.** При загрузке на пробу ядро перезапускает машину в срок, если `init` не подтвердил загрузку (351-KRN-0014).
- **Программа спрашивает `init`.** Каждую секунду программа обновления спрашивает `init`, как прошла загрузка (`init.wit` 1.4 `boot`, 000-KRN-0102; 351-UPD-0021). `init` отвечает, когда подтвердил или отверг загрузку.
  - Подтвердил: программа сразу пишет запись, подтверждающую работающий слот, тот же слот и тот же откат, подтверждено (`[UPDATER] SLOT … CONFIRMED ON THE DISK: INIT CONFIRMED THE TRIAL BOOT`).
  - Отверг: она ничего не пишет и ничего не делает сама. Ядро перезапускает машину в другой слот, который остаётся нетронутым.
- **Если `init` не может сказать** (`init` до версии 1.4), программа ждёт 5 с после срока ядра по тем же часам. Если машина к тому времени работает, загрузка была подтверждена, и программа пишет ту же запись.
- Пока проба не решена, программа ничего не делает сама.

**Записи.** Каждая запись пишется в файл, где нет более новой действительной записи, с её номером плюс один ([slots_RU.md](slots_RU.md)). Она пишется целиком, на место, и читается обратно. Номер, который не может вырасти ещё на два (проба и её неудача), не пишется. Запись выбирает `updater/src/plan.rs`; его хост-тесты используют кодирование самого загрузчика (`tests/updater_host.rs`).

## Выпуски в блочном хранилище (351-UPD-0033)

MC-9.3 требует, чтобы образы восстановления и нужные им объекты были защищены от обычной очистки. `updater` хранит свои выпуски в блочном хранилище ([docs/storage](../storage/README.md)), если носитель хранилища переживает перезапуск. При старте он говорит, так ли это: `[UPDATER] STORE: RELEASES ARE KEPT IN THE BLOCK STORE`, или почему нет (нет клиента, хранилище не смонтировано, RAM-диск).

- **Выпуск — дерево** в раскладке выпуска (`updater/src/kept.rs`):
  - `keys/current`, файл ключей, хранившийся с ним (351-UPD-0026);
  - `channels/<имя>`, канал, хранившийся с ним;
  - `releases/<версия>/<процессор>/MANIFEST` и `MANIFEST.SIG`;
  - блоб каждого файла, который манифест перечисляет для слота, под первыми двумя цифрами его имени (`blobs/ab/ab…`), чтобы ни один каталог не превышал блок.
- **Закреплён собственным владельцем `updater`.** Его клиент помечен `OWNER_UPDATER` ([351-STO-0006](../../issues-done/351-STO-0006-releases-pinned-in-the-store.done)). Сборка мусора не освобождает то, что держит закрепление, и ни один клиент другого владельца не снимает его, какие бы права у него ни были. Ни одно имя не указывает на выпуск: имя хранит свои версии, и они держали бы выпуск после снятия закрепления.
- **Когда выпуск кладётся:**
  - работающий — при старте и после подтверждения пробы, если хранилище его ещё не держит. Его манифест должен быть загруженным и подписанным загрузочным ключом, а канал — подписанным ключами выпусков из файла ключей, который хранит `updater`, и называющим его;
  - подготовленный — после того как `fetch` или `install-commit` записал его и его файлы прошли проверки.

  Каждый файл читается из слота (а приложение, которого в слоте нет, — из корня) и проверяется по размеру и SHA-256, пока кладётся. Блоб, который уже есть в хранимом выпуске, берётся из его дерева и заново не кладётся. Журнал говорит, что положено и что взято: `[UPDATER] STORE: VERSION 6 KEPT AS PIN …, ROOT …: … FILES, … BYTES PUT FROM SLOT B, … TAKEN FROM A KEPT RELEASE, IN … MS`.
- **Какие остаются** (`plan::keeps`), после подтверждённой загрузки и после подготовки:
  - работающий выпуск;
  - последний рабочий: новейший ниже работающего и не ниже минимума (наибольшего, что видел `updater`, или порога в записях), на который может откатиться `rollback`;
  - подготовленный выпуск выше работающего.

  Закрепления остальных снимаются (`[UPDATER] STORE: VERSION 4 LET GO (PIN 1)`), а журнал перечисляет, что осталось (`[UPDATER] STORE KEEPS VERSIONS 6, 5`). Пока работающий слот на пробе, ничего не снимается: другой слот тогда его запасной. Пока версия работающего неизвестна, тоже ничего не снимается.
- **Повреждённый слот записывается заново.** `rollback` сначала проверяет другой слот. Если он не совпадает со своим манифестом, последний рабочий выпуск из хранилища записывается туда заново, как из любого источника (`Source::Store`): его канал — по ключам выпусков файла ключей, который хранит `updater` (351-UPD-0027), и по версии, манифест — по каналу и загрузочному ключу, каждый файл — по размеру и SHA-256. Приложение, которое работающий слот держит в том виде, что перечислен, копируется оттуда. Срок действия канала не спрашивается, как и при откате. Затем слот проверяется так, как его проверит загрузчик, и загружается на пробу.
  - `apply` делает то же для подготовленного слота, который не совпадает со своим манифестом (351-UPD-0034), с выпуском, подготовленным там: только с той версией, которую назвал канал слота при запуске `updater` или при последнем `fetch`, выше работающей, и только если хранилище её держит. Срок действия канала тогда спрашивается, как при любом применении. Без такого выпуска применение отклоняется, как раньше (`digest` или `not-staged`).

## Распоряжения восстановления (351-UPD-0030)

Порог поднимают только собственные записи `updater`. Единственный путь ниже него, кроме записи диска вручную, — **распоряжение восстановления**: `recovery/<канал>` в источнике. Это одна строка JSON (`channel`, `expires`, `floor`, `sequence`, `version`) и строки подписей ключей роли **recovery** файла ключей, отдельной от ключей выпусков и меток. При каждой проверке, сразу после файла ключей, `updater` читает его, если оно есть, и применяет, когда:
- его подписали ключи восстановления хранимого файла ключей не меньше порога: `[UPDATER] RECOVERY ORDER 1 REFUSED: FEWER THAN 1 OF THE RECOVERY KEYS OF KEY FILE VERSION 1 SIGNED IT`;
- оно этого канала, не просрочено, и его номер выше последнего применённого: поданное снова отклоняется (`… REFUSED: NOT ABOVE ORDER 2, APPLIED BEFORE`);
- работающий слот подтверждён, а другой слот держит версию распоряжения и проходит проверку, как её сделает загрузчик; его канал подписан ключами выпусков хранимого файла ключей (351-UPD-0027).

Затем по порядку: распоряжение заносится в учёт, `system/updater/recovery` (строка `<канал> <номер> <версия> <порог> <его SHA-256>` на каждое, хранится так же, как файл ключей); пишется запись другого слота на пробу с одной попыткой и порогом, пониженным до указанного (`plan::recover`); `init` перезапускает машину: `[UPDATER] RECOVERY ORDER 2 OF CHANNEL stable APPLIED: VERSION 5 IN SLOT B ON TRIAL, THE FLOOR 6 LOWERED TO 5; …`. Отказ сообщается один раз, и проверка идёт дальше. После отзыва ключа распоряжение может указать на выпуск, подписанный новым ключом выпусков. Канал по-прежнему называет то, что называет: пока издатель его не изменит, устройство на более старой версии видит его предложение.

## Метаданные после срока действия

Устройство может прожить дольше срока своего канала без свежего: без сети или с источником, который не отвечает. Политика (MC-9.4; 351-UPD-0025):
- **Система работает дальше.** Она остаётся в своём подтверждённом слоте. Истечение срока останавливает обновления, но не систему.
- **Никакого обновления, пока не придёт свежий канал.**
  - `check` и `fetch` отклоняют просроченный канал (`expired`).
  - `apply` отклоняет подготовленный выпуск, если срок сохранённого с ним канала истёк.
  - Следующий автоматический запуск или запрос снова обращается к источнику.
- **`rollback` остаётся возможным.** Ему не нужна сеть, а минимум по-прежнему действует: версия не ниже наибольшего минимума, который видел `updater`.
- **Часы, которые не читаются,** означают, что срок истёк.
- **Об этом сообщается.**
  - В журнале: `[UPDATER] METADATA: CHANNEL … VERSION …, MINIMUM …, EXPIRES …, KEPT IN SLOT A` при запуске и `… FROM THE SOURCE` после каждой проверки, которая прочла другой канал. Когда срок истёк, строка кончается на `; EXPIRED: FETCH AND APPLY WAIT FOR A CURRENT CHANNEL`.
  - Клиенту: то же даёт `metadata` (`update.wit` 1.1).
- **Заморозка.** Источник, который раз за разом отдаёт один и тот же непросроченный канал, держит на нём устройство до истечения срока его метки времени: по умолчанию сутки, и продлить её можно только ключом меток (351-UPD-0028), а не на недели срока канала.

## update.txt

Файл в корне загрузочного тома. В работающей системе его ничто не пишет: он пишется вместе с образом или на другой машине.

```
source https://updates.example.org/mind   # или каталог: usb:releases на подключённом томе, data/link/rel на загрузочном
pin 3c5f…                                 # https: SHA-256 открытого ключа сервера; без него — tlsroots.pem
channel stable
automatic apply                           # none (по умолчанию), check, fetch или apply
every 21600                               # секунды между автоматическими запусками; 0 (по умолчанию) — один раз при старте
tries 3                                   # попытки загрузки на пробу при автоматическом apply (от 1 до 9)
```

- **Источник-каталог** проверяется так же, как HTTPS: источник только отдаёт байты, а все проверки выше делает программа обновления. Файл, размер которого не совпадает с манифестом, отвергается до копирования, и следующий запуск берёт его снова (351-KRN-0141).
- **Без файла** у `updater` нет своего источника, и на `check` и `fetch` он отвечает `no-source`. Каталог кабеля, ниже, он берёт и тогда.
- **Каталог кабеля, `data/link/rel/`, — источник всегда** (801-UPD-0039, решение сопровождающего от 2026-11-14 для 801-LNK-0044: кабель обновляет весь код без всяких разрешений). `link` пишет его как `rel/`, а заполняет `scripts/link_update.py`.
  - **Когда:** каждые 20 с, пока не ждёт проба, `updater` открывает там `timestamps/<канал>`. Как только этот файл изменился с прошлого раза, выпуск кладётся в слот и применяется, что бы ни говорили `source` и `automatic` в `update.txt`. Каталог без метки времени стоит одного открытия и в журнал ничего не пишет.
  - **Проверки — как для любого источника:** файл ключей как следующая версия доверенного, подписи и сроки метки времени и канала, подпись манифеста загрузочным ключом, размер и SHA-256 каждого файла, порог и минимум (MC-9.2–9.4). Так через кабель ставится только то, что подписали ключи `updater`. Выпуск не новее работающего записывается в журнал и не берётся.
  - **Канал** — тот, что в `update.txt` (без него `stable`). Записи метки времени и распоряжений восстановления хранятся по каналу, так что кабель и сетевой источник одного канала делят их, и побеждает более новый выпуск из любого.
  - **Журнал** называет его один раз при запуске: `[UPDATER] SOURCE data/link/rel (THE CABLE'S, 801-LNK-0044): ALWAYS, AUTOMATIC APPLY`. Если `update.txt` называет этот каталог своим `source`, его берёт этот путь.
- **Автоматический запуск** начинается, когда проба (если она есть) подтверждена. Если источник не отвечает, запуск повторяется через 30 с.
- **Источник** — сервер HTTPS или каталог с раскладкой `scripts/release.py`. Оба проходят одни и те же проверки.
- **HTTPS** идёт через сетевой грант, который политика сети даёт `updater`, поэтому `netpolicy.txt` должен называть сервер.

## Проверено

- **Проверка `update`** (часть набора `updater`; x86, aarch64). В образе выпуск 5 в слоте A, подтверждённый, с сохранённым каналом. `update.txt` называет тестовый сервер (`httpd` с крючками для тестов, [server_RU.md](server_RU.md)) по HTTPS, которому доверяют по закреплённому ключу, с `automatic apply` каждые 20 с.
  - Отклоняется каждое из следующего, и загрузочные записи остаются прежними (это видно по итоговым номерам):
    - просроченный канал;
    - канал с плохой подписью;
    - канал, называющий более старую версию;
    - версия 6 с одним изменённым на сервере загрузочным файлом.
  - Затем версия 6 в опубликованном виде загружается в слот B. Её самый большой загрузочный файл обрывается на середине и продолжается через `Range`.
  - В слоте A образа лежат приложения выпуска 5, и они запускаются оттуда (`[LOADER] APPLICATIONS FROM MIND/A/`).
  - Версия 6 отличается от 5 одним приложением, `uptime.elf`. Загружается только оно, остальные копируются из слота A, и после этого в слоте B есть все приложения в том виде, как их перечисляет манифест. Проба запускает их из слота B.
  - После загрузки снова в слот A, по записи, которую оставляет откат (её пишет хост), выпуск 5 запускает свои приложения из слота A, в том числе свой `uptime`.
  - Она проверяется и загружается на пробу через перезапуск `init`. Загрузчик загружает манифест выпуска 6.
  - Как только `init` подтвердил пробу, `updater` подтверждает слот B на диске, задолго до срока ядра, и затем не находит ничего новее.
  - В записях ровно три записи одного обновления: проба, отсчёт загрузчика, подтверждение. `fsck.fat` находит том согласованным.
  - Журнал называет канал, который держит `updater` (351-UPD-0025): при запуске — канал слота A, действующий, затем канал источника, просроченный.
  - После загрузки снова в слот A, с часами на 60 дней вперёд, после срока сохранённого там канала, и без сети, `updater` сообщает, что срок канала истёк, а система работает дальше: `uptime` запускается.
- **Набор `linkupdate`** (351-KRN-0141; x86, aarch64) отклоняет просроченный канал из каталога так же, как через HTTPS, не записав загрузочной записи.
- **Набор `updatestore`** (351-UPD-0033; x86, aarch64; идёт вместе с `updater`) работает с пустым диском хранилища, а `update.txt` ничего не просит делать самому.
  - При старте `updater` кладёт выпуск 5 в хранилище.
  - `update fetch` готовит выпуск 6 и тоже кладёт его. Кладутся только два файла, которые выпуск 6 меняет (`uptime.elf` и загрузчик), остальные берутся из дерева выпуска 5.
  - Хранилище пишет в журнал оба закрепления со значком `updater`, 23. У клиента оболочки закреплений нет, а снять закрепления `updater` ему отказано (`Rights`).
  - После применения и подтверждения хранилище держит оба выпуска. Сборка мусора освобождает объект, который никто не держит, а оба дерева читаются целиком через `blocks check <cid> tree`.
  - Перед применением, при выключенной машине, на диске меняется байт подготовленного ядра слота B (351-UPD-0034). Без сети `update apply` записывает выпуск 6 обратно из хранилища, и слот B загружается на пробу и подтверждается. Его ядро после этого такое, как опубликовано.
  - При выключенной машине ядро и загрузчик слота A портятся на диске. `update rollback` записывает выпуск 5 обратно из хранилища, и слот A загружается на пробу с манифестом выпуска 5 и подтверждается. Его файлы после этого такие, как опубликованы.
- **Хост-тесты** (`tests/updater_host.rs`) проверяют каждую запись `updater` и то, как по ней выбирает загрузчик:
  - проба обновления;
  - её подтверждение;
  - неудачная проба, после которой работает откат;
  - откат;
  - отсутствие действительной записи;
  - номер на пределе.

  Они же проверяют, как файлы манифеста делятся на загрузочные, приложения и общие файлы корня, и когда метаданные считаются просроченными: с секунды их срока или всегда, если часы не читаются. С 351-UPD-0033 они проверяют и выпуски в хранилище:
  - какие остаются;
  - чтение дерева выпуска по путям раскладки;
  - два выпуска с общими блобами, 400 блобов под своими префиксами;
  - отказ для деревьев неверной формы или повреждённых.

## Чего ещё нет

- **Вызывающего `idl/update.wit`.** Ни одна программа не держит клиента `updater`: команда `update` оболочки — задача трека инструментов (351-APP-0029, пронумерована на его ветке из [requests-APP.md](../../issues/requests-APP.md)), а слот для её клиента запрошен у трека ядра ([requests-KRN.md](../../issues/requests-KRN.md)). Поэтому `check`, `fetch`, `apply`, `rollback`, `status` и `metadata` в тестах работают только через автоматическую политику. `rollback`, `status` и `metadata` на платформе не запускались, как и отказ `apply` подготовленному выпуску с истёкшим сроком: автоматический запуск сначала проверяет источник.
- **Прочие отказы источника-каталога в QEMU.** Набор `linkupdate` (351-KRN-0141) берёт выпуск из `data/link/rel/`, загружает его на пробу и подтверждает, а просроченный канал и канал с изменённой подписью отвергает. Более старый канал, изменённый загрузочный файл и докачка проходят тот же `stage()`, что и через HTTPS, где каждый случай показывает набор `update`, но из каталога ни один из них не запускался.
- **Собственная сторона шлюза Effector в `install`** (751-EFF-0023). Набор `install` (идёт вместе с `updater`, 751-UPD-0032) передаёт пакеты через заместителя: `tests/updater_stub` на месте effector_gw, с клиентом шлюза.
  - При выключенном `remote-update` каждый `install-begin` и `install-commit` получает `denied` и попадает в журнал.
  - При включённом:
    - пакет, в загрузочном файле которого изменён один байт, отклоняется (`digest`);
    - так же отклоняются пакет, чей манифест подписан другим ключом (`signature`), и пакет, оборванный после первого куска (`digest`);
    - пакет выпуска 6, один кусок которого записан дважды, ставится в слот B и удаляется;
    - `apply` загружает слот B на пробу, и проба подтверждается.

  Набор прошёл в QEMU на x86 и aarch64. Чтение пакета также проверяют тесты на хосте (`tests/updater_host.rs`): на пакете, записанном `release.py bundle`, и на враждебных архивах. Клиент с другим значком против вызовов установки ещё не запускался: команды `update` в оболочке пока нет.
- **Выпуски в хранилище: чего ещё нет** (351-UPD-0033):
  - `update` в оболочке не показывает, какие выпуски держит хранилище: `kept` (1.5) отдаёт их клиенту, а команда оболочки — дело трека инструментов ([requests-APP.md](../../issues/requests-APP.md)). Журнал их показывает.
  - Подготовленный выпуск, которого хранилище не держит или канал слота которого не читается при запуске `updater`, `apply` обратно не записывает: `fetch` записывает его заново из источника.
  - Сборка мусора в ту минуту, что проходит между записью блока и закреплением дерева, может освободить блок. Тогда закрепление отклоняется (`incomplete`), и выпуск кладётся при следующем старте.
  - Счёт `updater` считает каждый выпуск целиком, поэтому трём выпускам нужны три четверти носителя размером в четыре выпуска. Четверть носителя оставлена за ним, что бы ни удерживали другие владельцы (351-STO-0043); сверх неё он занимает то, что оставили другие.
  - На реальном оборудовании ничего из этого не запускалось.
- **SSH** (351-NET-0004).
- **Защита от отката** сверх проверки версии: откат загружается при любой версии (351-UPD-0009, 0011).
- **Смена и отзыв ключей** (351-UPD-0009). Загрузчик не обновляется (351-UPD-0010).
- **Образов со слотами по умолчанию.** `make_usb_image.py --slots` делает образ, который программа обновления может обновлять ([write-disk_RU.md](../write-disk_RU.md), 351-UPD-0016); без этого ключа образ загружается из корня, и заполнять ему нечего.
- **Часы.** Срок действия надёжен ровно настолько, насколько надёжны системные часы, а второго источника времени у `updater` нет.
