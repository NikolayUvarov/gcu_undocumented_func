# Запись MIND Core на диск и загрузка ПК

**Версия:** 1.5 (2026-10-28): раздел хранилища, `MIND STORE` (307-STO-0020); 1.4 (2026-10-20): одна загрузка MIND Core из Linux (раздел 10) · **Задачи:** [211](../issues/211-intel-pc-from-a-sata-ssd.md) (ПК с Intel с SATA SSD), [211-PRT-0001](../issues/211-PRT-0001-writer-for-an-internal-disk.md) (скрипт записи), [211-PRT-0004](../issues/211-PRT-0004-first-run-on-an-intel-pc.md) (первый запуск), [211-PRT-0006](../issues/211-PRT-0006-log-partition-in-the-image.md) и [211-KRN-0019](../issues-done/211-KRN-0019-boot-logs-on-the-log-partition.done) (раздел журналов), [000-KRN-0124](../issues/000-KRN-0124-switching-between-linux-and-mind-core.md) (одна загрузка из Linux) · **English version:** [write-disk.md](write-disk.md) (основной текст; этот перевод держится в согласии с ним)

> **Ни одна физическая машина x86 пока не входит в доказательства работы MIND Core.** Всё ниже следует из скриптов и из QEMU, где тот же образ загружается с USB, SATA (AHCI) и NVMe. Первый настоящий запуск — задача [211-PRT-0004](../issues/211-PRT-0004-first-run-on-an-intel-pc.md). В разделе 8 — что известно как рискованное на реальном ПК, в разделе 9 — что прислать.

## 1. Что нужно

- **Машина с Linux:** Python 3, util-linux (`lsblk`, `findmnt`, `blockdev`) и `sudo`. Для сборки образа нужны инструменты проекта (`./01_prepare_env.sh`) и `qemu-img` (идёт с QEMU).
- **Диск, данные на котором можно потерять**, от 1 ГиБ (образ занимает 568 МиБ). Подойдёт любой из:
  - USB-флешка;
  - SSD в USB-SATA адаптере или боксе (например, Samsung 860 PRO);
  - SATA- или NVMe-диск внутри Linux-машины, с опцией `--internal` (раздел 4). Только не тот диск, с которого работает сам Linux: такой скрипт не примет ни при каких ответах.
- **ПК для загрузки:** x86-64 с UEFI. Загрузка через Legacy BIOS не поддерживается.

## 2. Собрать образ

```bash
./04_make_usb_image.sh --force
```

Скрипт собирает всё и пишет `dist/mind-core-usb.img` (около 700 МиБ). В его MBR три раздела:

- **`MIND CORE`**, загрузочный том: FAT16 с типом системного раздела EFI. В нём `EFI/BOOT/BOOTX64.EFI`, ядро, службы и программы.
- **`MIND LOG`**, том журналов: 64 МиБ FAT16 обычного типа, который Windows, macOS и Linux подключают сами. MIND Core пишет туда системный журнал каждой загрузки, `BOOTNNNN.LOG` (раздел 9).
- **`MIND STORE`**, раздел блочного хранилища (307-STO-0020): 128 МиБ с типом MBR `0x7F`, который другие системы не подключают. В нём пустое хранилище: суперблок хранилища, затем пустые секторы. MIND Core его пока не использует: на настоящей машине хранилище работает на RAM-диске, пока `init` не отдаст ему этот раздел ([307](../issues/307-the-stores-own-partition.md)).

Скрипт проверяет каждый упакованный файл и все три раздела и печатает SHA-256 образа. `--force` заменяет старый образ; без опции существующий образ остаётся.

С `--slots` ядро, службы, приложения (351-UPD-0023) и подписанный манифест кладутся в слот A (`MIND/A/`), подтверждённый в `MIND/BOOT0`, чтобы программа обновления могла заполнить слот B ([docs/update/updater_RU.md](update/updater_RU.md)). `--channel ФАЙЛ` сохраняет в слоте A подписанный файл канала выпуска, и тогда программа обновления знает работающую версию; его манифест должен быть манифестом этой сборки. `--update ФАЙЛ` кладёт в корень `update.txt`.

Необязательно: сначала загрузить этот же образ в QEMU как USB-флешку.

```bash
python3 tests/usb_image_smoke.py --qemu qemu-system-x86_64 --firmware OVMF.fd
```

## 3. Найти диск

```bash
./05_write_usb_linux.sh --list              # USB-диски
./05_write_usb_linux.sh --list --internal   # ещё и SATA и NVMe внутри этой машины
```

В каждой строке — путь, размер, модель, серийный номер и шина. Диск с файловыми системами самого Linux помечен `SYSTEM DISK: REFUSED`. Используйте постоянное имя целого диска `/dev/disk/by-id/…` (`ls -l /dev/disk/by-id/`), а не раздел вроде `/dev/sdb1`.

## 4. Проверить без записи

```bash
./05_write_usb_linux.sh --device /dev/disk/by-id/usb-Samsung_SSD_860_PRO_…  --check
./05_write_usb_linux.sh --device /dev/disk/by-id/ata-Samsung_SSD_860_PRO_…  --internal --check
```

`--check` не требует root и ничего не пишет. Он показывает образ, его SHA-256, диск и каждый раздел на нём — файловую систему, метку и точку монтирования. То есть всё, что запись уничтожит.

## 5. Запись: скрипт спрашивает перед записью

```bash
./05_write_usb_linux.sh --device /dev/disk/by-id/…            # USB-диск
./05_write_usb_linux.sh --device /dev/disk/by-id/… --internal # внутренний SATA- или NVMe-диск
```

Скрипт спрашивает по порядку:

1. **Пароль `sudo`.** Если скрипт запущен не от root, он сам перезапускается через `sudo`.
2. **Диск.** Скрипт печатает `ALL DATA ON THIS DISK WILL BE LOST:`, модель, серийный номер, размер и шину диска и все разделы на нём.
3. **Запрос `1/2`:** введите серийный номер диска. Если диск его не сообщает — модель, а если нет и её — имя устройства. Ожидаемый текст показан в скобках. Так вы подтверждаете, что выбрали именно этот диск.
4. **Запрос `2/2`:** введите `ERASE /dev/sdX` — с путём диска, как он показан в запросе.

Любой другой ответ на любой из запросов останавливает скрипт, и на диск ничего не пишется.

Дальше скрипт:

- ещё раз проверяет, что диск тот же, и отмонтирует его файловые системы;
- открывает его монопольно и пишет образ, показывая ход записи;
- стирает старые данные GPT в конце диска;
- читает образ обратно и сверяет SHA-256.

`Done. SHA256 matches.` значит, диск готов. Отменённая или сорвавшаяся запись может оставить неполный образ — запустите скрипт ещё раз.

Скрипт откажется при любых ответах, если диск:

- тот, с которого работает Linux: на нём `/`, `/boot`, `/boot/efi`, `/usr`, `/var` или `/home`;
- хранит сам образ или репозиторий;
- занят LVM, RAID или шифрованием, или на нём активный swap;
- только для чтения, меньше образа или с логическим сектором не 512 байт. Некоторые USB-SATA адаптеры сообщают сектор 4096 байт; возьмите другой адаптер или `--internal`.

Остаток диска, если он больше образа, не используется.

В Windows `05_write_usb_windows.ps1` пишет только USB-диски (README, раздел «Write the image from Linux or Windows»).

**Из WSL в Windows, одним шагом:** `scripts/build_and_write.sh <номер диска>`.
- Он забирает `fast-test` (или собирает `--commit <id>`), собирает систему и упаковывает образ.
- Он открывает PowerShell с правами администратора, где `05_write_usb_windows.ps1` спрашивает перед записью (`ERASE <номер>`).
- После записи он копирует на диск проприетарные файлы и картинки рабочего стола, а также тестовые файлы, которые просят его ключи: `--link-dev`, `--keep-wifi`, `--wifi-ofdm` и другие, перечисленные в начале скрипта.
- **`--slots`** пишет образ со слотами загрузки и `update.txt`, который берёт выпуски из `data/link/rel/`. После этой одной записи `scripts/link_update.py` обновляет машину через линк (351-KRN-0141).
- **`--mode=maintenance`** кладёт на диск `data/mode.conf` с этой одной строкой, так что `init` стартует в режиме обслуживания и запускает службы агента Effector (750-KRN-0143). Так же работают `--mode=development` и `--mode=development,maintenance`.
- **`link-console`** можно поставить рядом с ними, вместе с `--link-dev`: например, `--mode=maintenance,link-console`. Тогда `init` принимает линк как консоль владельца (800-KRN-0155, 800-LNK-0019). Без `dev` в `link.conf` `init` пропускает это слово, поэтому без `--link-dev` скрипт его не примет. Включить или выключить его можно только словом на диске: команда `mode` в оболочке его не меняет.
- **`--keep-effector`** сохраняет агента Effector при записи. Перед записью `data/effector/` (его настройка и политика владельца) и `system/effector/` (его ID, журнал и токен) сохраняются со старого диска в `~/.config/mind/effector`, с правами 700 и 600. После записи они возвращаются на диск и сверяются. С `--mode=maintenance` агент поднимается тем же узлом, без шага за клавиатурой и без новой активации на сервере (800-LNK-0023). В файлах может быть токен агента: не печатайте и не коммитьте их.
  - **Вставьте старый диск до записи,** если указаны `--keep-wifi`, `--keep-effector` или `--keep-settings`: сохраняемое снимается с него до того, как откроется окно записи. Если диска нет, скрипт попросит его вставить и подождёт до 10 минут; Enter — продолжить без него, тогда вернётся то, что было сохранено раньше.
  - **Перед тем как вынуть диск, выключите машину или перезагрузите её.** Файловый сервис MIND Core держит последние изменения в кэше, и `rm` или `mv` попадают на диск только при сбросе кэша (запрос KRN, 2026-10-24). На диске, вынутом из работающей машины, их может не оказаться, и сохранять будет нечего: так 2026-10-24 пропал `effector.conf` агента Effector. Сбросить кэш можно и командой `sync` в оболочке.
- **`--keep-settings`** сохраняет всё, что настроил владелец: `--keep-wifi` и `--keep-effector`, а также остальное из `data/` и `system/`. Это часовой пояс (`data/clock.conf`), рабочий стол (`data/wm.conf` и его картинка), `data/memory.conf`, `data/services.txt`, `data/mode.conf`, установленные приложения и файлы владельца. Они сохраняются в `~/.config/mind/settings` и возвращаются первыми, так что ключ, данный сейчас (`--mode=` и другие), всё равно побеждает (800-LNK-0024). Не сохраняется то, что скрипт кладёт сам (`data/firmware`, `data/wallpapers`, тестовые флаги), и `data/link`.
- `--list` показывает USB-диски и их номера.
- Он собирает тот репозиторий, в котором лежит, в том числе когда его запускают по символической ссылке извне.

## 6. Загрузить ПК

**Настройки прошивки** (экран настройки, обычно Del, F2 или F10 при включении):

- режим загрузки **UEFI**; CSM или «Legacy» **выключить**;
- **Secure Boot выключить**: загрузчик пока не подписан (задача [350](../issues/350-signed-boot-images.md));
- режим SATA **AHCI**, а не RAID, Intel RST или VMD;

**Диск:**

- либо внутри ПК, на первом SATA-порту (`SATA0`/`SATA1` на плате);
- либо в том же USB-адаптере, в заднем USB-порту.

Для первой проверки отключите остальные диски и флешки ПК: программы могут читаться с тома FAT другого диска (раздел 8).

**Запуск:** выберите UEFI-запись диска в меню загрузки прошивки (часто F8, F11 или F12) или поставьте её первой в порядке загрузки.

**Mac с Intel** (например, MacBook Pro 2012–13; пока не проверялось, [211-PRT-0004](../issues/211-PRT-0004-first-run-on-an-intel-pc.md)):

- **Запуск.** Подключите диск по USB, при включении держите Option (⌥) и выберите его запись `EFI Boot`.
  - На Mac без чипа T2 в прошивке ничего менять не нужно.
  - На Mac с T2 (с 2018 года) в «Утилите безопасной загрузки» нужно выбрать «Без защиты» и «Разрешить загрузку с внешних носителей».
- **Перезапуск в MIND Core.** Выбор, сделанный с Option, действует только на одну загрузку. Любой перезапуск снова запускает macOS, в том числе `mindlink reboot`: так было на MacBook Pro 2026-10-21.
  - **Чтобы диск стал загрузочным по умолчанию,** один раз выполните в «Терминале» режима восстановления macOS, с подключённым диском. Из самой macOS это запрещено (ниже).
    - macOS подключает только раздел журналов, `MIND LOG`. Загрузочный раздел помечен как системный раздел EFI (тип `0xEF`), такие macOS не подключает, поэтому его сначала подключают вручную.
    - Диск, на котором лежит `MIND LOG`, — это флешка, например `disk2`, а загрузочный раздел — первый на ней, `disk2s1`.

    ```bash
    diskutil info "/Volumes/MIND LOG" | grep "Part of Whole"     # флешка, например disk2
    sudo mkdir -p /Volumes/MINDCORE
    sudo mount -t msdos /dev/disk2s1 /Volumes/MINDCORE           # её загрузочный раздел
    sudo bless --mount /Volumes/MINDCORE --setBoot --file /Volumes/MINDCORE/EFI/BOOT/BOOTX64.EFI --shortform
    bless --getBoot                                              # какое устройство прошивка запускает теперь
    sudo umount /Volumes/MINDCORE
    ```

    `bless` записывает диск в настройки прошивки (NVRAM). После этого Mac должен запускать его при каждом включении и перезапуске, пока он подключён, а без него — macOS.
  - **Где это работает: режим восстановления macOS.** При включении держите Command-R, затем «Утилиты», «Терминал». Там вы root, поэтому без `sudo`. Номера дисков там могут отличаться: найдите флешку командой `diskutil list`.
    - **На MacBook Pro 2026-10-21 из режима восстановления это сработало.**
    - После этого `mindlink reboot` возвращал Mac в MIND Core примерно за 9 с, без нажатия клавиш, и Wi-Fi подключался снова.
  - **Из самой macOS это запрещено.** С подключённым разделом `bless` ответил `Could not set boot device property: 0xe00002e2`. Это `kIOReturnNotPermitted`, запрет защиты целостности системы macOS (SIP, с 10.11); `bless --getBoot` по-прежнему показывал том macOS.
  - **Перезапись может его сбросить.** 2026-10-21 после новой записи диска Mac запустил macOS, а 2026-10-22 — диск. Если запустилась macOS, повторите команды из режима восстановления. На диске, записанном с `--slots` (раздел 5), загрузчик лежит там же, поэтому команды те же. Обновления через линк диск не перезаписывают. С 351-UPD-0010 это не нужно и для нового загрузчика: каждый выпуск приносит свой в свой слот, и загрузчик из `EFI/BOOT/` его запускает ([slots_RU.md](update/slots_RU.md)). Флешка, записанная до этой задачи, загружает каждый слот своим старым загрузчиком, поэтому её записывают ещё раз.
  - **Чтобы macOS снова загружалась по умолчанию:** «Системные настройки», «Загрузочный диск», диск с macOS.
- **Внутренний диск.** На нём остаётся свой EFI-раздел:
  - загрузчик читает только тот диск, с которого запущен ([211-KRN-0012](../issues-done/211-KRN-0012-boot-volume-identity.done));
  - `vfs_server` монтирует только тома FAT в таблице разделов MBR, поэтому GPT внутреннего диска он пропускает.
- **Нет COM-порта.** Вместо него о происходящем говорят:
  - ход загрузки и ошибки загрузчика, текстом ([211-KRN-0015](../issues-done/211-KRN-0015-boot-errors-on-a-mac-screen.done), [211-KRN-0016](../issues-done/211-KRN-0016-the-screens-gop-and-boot-progress.done));
  - строки загрузки ядра и его остановки ([211-KRN-0013](../issues-done/211-KRN-0013-fatal-messages-on-the-screen.done)).
- **Клавиатура и трекпад.** Это USB-устройства внутри Mac. На чипсетах Intel 7–9 серий ядро переводит порты USB с контроллеров EHCI на xHCI до запуска `usb_host`.

## 7. Как выглядит удачная загрузка и что проверить

Загрузчик читает с диска ядро и службы, экран переключается на MIND Core, появляется приглашение оболочки `MIND>`. Дальше:

```
cpus                       # все ядра в сети
svc                        # службы работают; среди них ahci (внутренний диск) или usb_storage (USB)
ls                         # программы на диске
run clock                  # программа (Esc завершает)
write data/hello first boot
sync
reboot
cat data/hello             # после перезагрузки: файл сохранился
ls log:                    # раздел журналов: по BOOTNNNN.LOG на каждую загрузку
```

## 8. Если остановилось

| Что видно | Вероятная причина | Что делать |
|---|---|---|
| `BOOT ERROR: display: …` | Прошивка не даёт линейный кадровый буфер (GOP) | Другой видеовыход или встроенная графика; сообщите |
| `BOOT ERROR: kernel.elf: …`, `BOOT ERROR: <имя>.elf: …` или `BOOT ERROR: boot volume: …` | На диске, с которого запущен загрузчик, нет файла или он повреждён, либо прошивка не видит на этом диске файловой системы. Загрузчик читает только свой диск ([211-KRN-0012](../issues-done/211-KRN-0012-boot-volume-identity.done)) | Запишите диск заново (раздел 5) |
| Оболочка работает, но программы не запускаются или `ls` пуст; `logs` службы `vfs_server` (её PID — из `ps`) пишет `THE BOOT VOLUME (…) IS ON NO BLOCK DEVICE` | `vfs_server` подключает только тот том, с которого прочитан загрузчик, а этот диск не показывает ни один драйвер (например, контроллер, для которого в MIND Core нет драйвера) ([211-KRN-0012](../issues-done/211-KRN-0012-boot-volume-identity.done)) | Подключите диск к другому порту или шине (USB в задний порт, первый порт SATA) |
| Серые строки `MIND CORE KERNEL: …`, затем белый текст на тёмно-красном: `KERNEL PANIC`, `KERNEL EXCEPTION` или `INIT EXITED` | Ядро остановилось, и красный текст говорит почему ([211-KRN-0013](../issues-done/211-KRN-0013-fatal-messages-on-the-screen.done)). | Сфотографируйте экран |
| Остаётся картинка прошивки (у Mac — вращающийся индикатор), и ни одной строки `MIND CORE BOOT:` | Прошивка не запустила загрузчик, или её консоль не переключилась в текст | Сообщите, указав, какой пункт меню загрузки выбрали |
| Строки `MIND CORE BOOT:` кончаются на `STARTED; READING …` | Загрузчик остановился, пока прошивка читала файлы с диска | Другой USB-порт или адаптер; сообщите, приложив фото |
| Строки `MIND CORE BOOT:` кончаются на `… EXITING BOOT SERVICES`, и от ядра ничего не появляется | Ядро остановилось до того, как взяло экран, или GOP, выбранный загрузчиком (`USING GOP`), — не тот, что на экране; строки `GOP` перечисляют все, что есть у прошивки ([211-KRN-0016](../issues-done/211-KRN-0016-the-screens-gop-and-boot-progress.done)) | Сфотографируйте строки. Кабель в COM1, если он есть на плате, покажет причину |
| Оболочка работает, но `ls` пуст или `[INIT] ahci NOT STARTED` | SATA в режиме RAID/RST/VMD или диск не на первом SATA-порту ([211-DRV-0002](../issues/211-DRV-0002-ahci-every-port.md)) | Режим AHCI; первый порт |
| `MIND CORE KERNEL: NO TICK FROM THE PIT` или всё ждёт бесконечно (программы со сном, время стоит) | До ядра не доходят прерывания таймера. Строка `MIND CORE KERNEL: TICK: …` говорит, откуда тик: от таймера LAPIC или от PIT, если прошивка не указала таймер ACPI PM ([211-PRT-0003](../issues-done/211-PRT-0003-tick-without-the-pit.done)) | Сфотографируйте строки и сообщите |
| Клавиатура не работает | Работают только PS/2 и USB-клавиатуры на первом контроллере USB 3 (xHCI); на чипсетах Intel 7–9 серий ядро сначала переводит туда порты USB с EHCI | Другой USB-порт (задний, от чипсета) или клавиатура PS/2 |

**Паузы для фото экрана.** По умолчанию загрузка не ждёт. Чтобы сфотографировать экраны загрузки, запишите число секунд (не больше 60) в `data/pause.txt` на загрузочном томе: из Windows на записанной флешке или в MIND командой `write data/pause.txt 5` и перезапуском. Тогда на столько задержатся три экрана:

- строки прошивки (`A PAUSE OF 5 S: THE LINES ABOVE ARE THE FIRMWARE'S`);
- строки загрузчика `MIND CORE BOOT:` (`A PAUSE OF 5 S FOR A PHOTO OF THESE LINES`);
- серые строки ядра, пока compositor не забрал экран.

`0` или нет файла — паузы нет (211-KRN-0089). Загрузка, которая не удалась, и так останавливается с ошибкой на экране.

## 9. Что прислать

Для задачи [211-PRT-0004](../issues/211-PRT-0004-first-run-on-an-intel-pc.md), получилось или нет:

- модель платы или ПК, процессор, версию прошивки;
- использованные настройки прошивки (раздел 6);
- как был подключён диск: внутренний SATA-порт или USB-адаптер;
- **файлы раздела `MIND LOG`.** Подключите диск к любому компьютеру и скопируйте с него `BOOTNNNN.LOG`:
  - каждый файл — системный журнал одной загрузки; он пишется каждые 2 секунды, поэтому доходит до последних секунд перед зависанием;
  - `HWNNNN.TXT` рядом — отчёт об оборудовании той же загрузки (174-KRN-0038): процессор, карта памяти и таблицы ACPI прошивки, все функции PCI и собственные строки ядра (`MIND CORE KERNEL: …`), включая те, что экран не сохранил;
  - в папке `ACPI` лежат таблицы ACPI прошивки отдельными файлами (`DSDT.bin`, `FACP.bin`, …);
- фото экрана там, где остановилось, или вывод `cpus`, `svc`, `stat devices` и `physmap`, если оболочка поднялась;
- вывод последовательного порта, если был кабель в COM1.

Профиль записывает машину как отдельную конфигурацию: что на ней запускалось и с какими настройками прошивки (MC-12.1).

## 10. Одна загрузка MIND Core из Linux и обратно

На ПК, где Linux стоит на своём диске, MIND Core можно запустить с флешки один раз, без загрузочного меню прошивки ([000-KRN-0124](../issues/000-KRN-0124-switching-between-linux-and-mind-core.md)). Любой перезапуск после этой загрузки возвращает в Linux. На Ryzen, где стоит Ubuntu, прогон выглядит так:

```bash
./05_write_usb_linux.sh --device /dev/disk/by-id/…   # раздел 5
sudo scripts/boot_switch.py status                   # записи загрузки (Linux первым) и диск MIND Core
sudo scripts/boot_switch.py once --reboot            # следующая загрузка, один раз, — с флешки
# … прогон в MIND Core; его reboot, паника, сторожевой таймер или отключение питания возвращают Linux …
sudo scripts/boot_switch.py logs ~/mind-runs         # том MIND LOG копируется, только чтение
```

**Как это устроено.** У прошивки две переменные:
- **`BootNext`** называет запись для следующей загрузки, и прошивка удаляет её в начале этой загрузки;
- **`BootOrder`** называет все загрузки после неё.

`once` ставит `BootNext` на запись флешки. Если у флешки записи нет, `once` сначала создаёт её командой `efibootmgr --create-only` с именем `MIND Core`. Ни образ, ни загрузчик не меняются.

**От чего скрипт отказывается**, объясняя причину:
- запись Linux (`BootCurrent`) не первая в `BootOrder`: перезапуск не вернул бы в Linux. Поставьте её первой в настройках прошивки;
- Linux запущен не через UEFI;
- диска MIND Core нет или их несколько (укажите один через `--disk`);
- диск MIND Core смонтирован.

`BootOrder` скрипт никогда не пишет.

**`logs`** копирует весь том `MIND LOG` в новый каталог и сообщает одно из двух:
- MIND Core загрузилась после `once`: какие новые `BOOTNNNN.LOG` она записала и завершился ли `autorun.msh`;
- она не загрузилась. Прошивка может пропускать USB-диски при включённом Fast Boot или не выполнять `BootNext`; Secure Boot с ключами Microsoft отвергает загрузчик (раздел 6).

**Прогон без человека.** После записи положите `autorun.msh` в корень флешки. Оболочка выполняет его один раз при старте ([docs/msh_RU.md](msh_RU.md)), и он может закончиться командой `reboot`. Например, `check` пишет свой полный журнал в `log:`:

```
#!msh
requires: files sysinfo log lifecycle
check
reboot
```

`diag/full.msh`, скопированный как `autorun.msh` и дополненный строкой `reboot` в конце, делает полный аппаратный прогон. Шаг, который спрашивает пользователя (камера, переменные прошивки), ждёт ответа, поэтому в прогоне без человека такие шаги лучше убрать.

**Зависание.**
- На ПК с Intel сторожевой таймер чипсета перезапускает машину в пределах 30 с, и этот перезапуск — загрузка Linux.
- На Ryzen то же делает сторожевой таймер AMD FCH ([213-KRN-0125](../issues/213-KRN-0125-the-amd-fch-watchdog.md)). Он проверен только на модели своих регистров, поэтому первые прогоны покажут, работает ли он: строка загрузки `WATCHDOG: AMD FCH, A RESET AFTER 30 S ...` говорит, что он взведён. Если там `WATCHDOG: NONE`, зависание ждёт кнопки питания.

**Машины Effector.** На машине, где работает Effector (Ryzen — одна из них), `once --reboot` запускает только сопровождающий, убедившись, что активных операций нет ([docs/effector_RU.md](effector_RU.md)).
