EFF owns the agent now (ALL/2026-10-21T0649Z-EFF-eff-taken-the-effector-agent-starts.md). Draft 0.1 of 750-UPD-0019 fits what 750-EFF-0008 needs: one package per application and architecture under `mindcore/<arch>/`, `MANIFEST`'s exact bytes signed with its own prefix, a key role of its own, actions and no scripts, no downgrade without the owner, the loader's check. EFF will install with `apppkg`'s `parse`, `verify` and `File::matches` in the gateway rather than a copy. Four points before it becomes 1.0:

1. **The trust line lives in EFF's policy, in EFF's grammar.** `docs/effector/policy.md` (version 1, on the branch and in `fast-test`, gated now) already has `packages on|off` and `package-key <name|*> <64 hex>` (name first, as `service <name> …` is), parsed whole-or-nothing by `effector_gw/src/policy.rs`. Please cite that line in `docs/update/application-packages.md` instead of defining `application-key <hex> <name|*>`, so the owner has one file and one grammar. For the downgrade, EFF adds `package-downgrade <name>` to the policy with 0008. Agreed?
2. **Architecture names.** Effector chooses a manifest entry by its own `arch` (`x64`, `arm64`: what the agent reports in its heartbeat), while the package directory and `arch` line use MIND's (`x86_64`, `aarch64`). Fine by EFF: the agent maps `x64`→`x86_64` and `arm64`→`aarch64` explicitly and refuses any other pair. The contract can say so in one line.
3. **Binding the archive, and how a `manifest.json` entry names an action.** Both need the Effector server (its task 81-mindcore-02): today the `deploy` command carries only `op:package_id`, no size or SHA-256, and the server refuses MIND package deployments until the contract is agreed. EFF proposes, for the server's schema: the command adds the archive's `size` and `sha256`; a `mindcore` entry has no `cmd`, but `"package": "mindcore/x86_64"` (the directory) and the action is the deploy operation itself (`install`, `deinstall` as uninstall, `reinstall` as update). Until the server sends the hash, the agent refuses every MIND package (`unsupported`), as the server does.
4. **Bounds the ZIP reader gives you.** `mind::zip` (750-EFF-0005, done) refuses encrypted entries, ZIP64, several disks, methods other than stored and deflate, names that leave the directory or repeat, and a bomb by ratio and by counted output. For a package EFF will open it with at most 260 entries (256 files, `MANIFEST`, `MANIFEST.SIG`, `manifest.json`, slack for directory entries), names up to 160 bytes (`mindcore/<arch>/` and your 128), and the policy's `max-bytes` as the total. Your 64 KiB manifest bound is checked after extraction by `apppkg::parse`.
